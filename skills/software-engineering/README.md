# 软件工程技能：缺陷复现与最小修复

> 这是一个装在 AI agent 上的技能包：它把「修一个 bug」约束成一条固定通路，并要求每一步都留下能被别人复核的文件。版本号见 `SKILL.md` 开头的 `version`，本文件不重复。

## 这个技能做什么

**只有一个场景**：你有一个**已有的代码仓**和**一条能稳定复现的失败**（报错文本、失败用例、可重复的异常），要定位并修好它，还要拿出证据。

它固定产出四件东西：

| 产出 | 是什么 |
|---|---|
| 复现记录 | 失败命令、退出码、两次运行的失败输出摘要，证明「不是偶发」 |
| 失败测试 | 一个能独立跑、在修复前必定失败的用例 |
| 补丁文件 | 只改必要文件、只改必要行的 `fix.patch` |
| 验证日志 | 三段：修复前失败、修复后通过、撤掉补丁再次失败 |

流程只有一条：**复现 → 定位并最小修复 → 验证**。复现不出来就停下来上报，不进入下一步；不允许跳过复现直接给补丁。

**适用面**：复现必须能在单进程、无子进程、无目录／文件级夹具的条件下表达。当缺陷只能通过子进程断言、或需要目录／文件级夹具才能复现时，本技能不适用——应停在 S1／前置判据并上报（`escalate`），不得改写成单进程观测来强行套用。

## 这个技能不做什么（十方面）

| 方面 | 一句话理由 |
|---|---|
| 1 系统结构与架构风格 | 修复不改结构，改结构就不是最小修复 |
| 2 模块拆分 | 重新划分模块属于设计工作，不是补丁 |
| 3 接口与契约设计 | 改接口会影响调用方，单点修复的验证覆盖不到 |
| 4 数据架构与数据归属 | 数据迁移不可逆，这条通路没有回滚验证 |
| 5 并发与时序编排 | 时序／并发问题无法用单测稳定复现，通过条件不成立 |
| 6 性能、可用性等质量目标 | 没有基线就无法判断「做完了」 |
| 7 技术决策记录与复审 | 产出决策文档会引入第二类交付物，破坏单通路 |
| 8 测试策略与覆盖率规划 | 这里只加一个复现用例，测试计划是另一类交付物 |
| 9 部署与架构守护 | 部署无法在本通路内回滚验证 |
| 10 文档化表达与概念落地 | 写作类交付物与这里的验收方式不同 |

另需注意：**它不改变模型本身能做什么**，只是把「修一个 bug」这件约束在一条通路里。能力边界只由「明确不做」和四类交付物定义；想扩边界，必须同时新增交付物类型、新增判定它的自动检查、从「不做」里移除对应条目并记一次版本，只改说法不算。

## 对强模型的好处

| 好处 | 依据 |
|---|---|
| 少跑偏：状态路由表规定「什么时候只加载哪一份阶段说明」，模型不用每次重新规划流程 | 【设计推断】 |
| 结论可核对：四件交付物都有固定格式，八项自动检查可重复运行 | 【已实测】示例仓上八项自动检查全部通过 |
| 不容易「看起来修好了」：验证日志强制三段，撤掉补丁必须再次失败；根因无直接证据时只能写「未验证根因」 | 【已实测】三段日志在示例仓可复现；**「因此不会冒充修复」属设计推断** |
| 省上下文：技能按状态只加载一份阶段说明，不必把全部规则常驻 | 【设计推断】 |

## 对弱模型的好处

| 好处 | 依据 |
|---|---|
| 不依赖参数记忆：步骤、产出格式、失败处理都写在文件里，照着做即可 | 【设计推断】 |
| 判不了就报「无法判定」，缺约定不猜、不补值，减少编造 | 【设计推断】 |
| 每一步都有明确的完成条件，模型不必自己发明「做到哪算完」 | 【设计推断】 |
| 用同一套文件把大模型的做法固定下来，小模型按图执行可减少方差 | 【设计推断】 |

**弱模型验收至今没有做。** 上面四条都只是设计推断，没有小参数模型的实测证据；本技能没有被验证「能让弱模型达到强模型水平」，也不构成任何「提升」结论。现有路由自测由同一模型族完成，按约定**不构成验收通过**。

## 企业场景（适用于……因为……）

| 场景 | 为什么这套形态有用 | 边界 |
|---|---|---|
| 有审计要求的团队 | 适用于需要「修复可追溯、证据可复跑」的团队：四件交付物＋三段验证日志都是文件，任何人可重跑命令核对；卡点日志默认不上传，人审后才决定提交 | **不声明满足任何合规标准**（如审计、等级保护、行业规范）；是否满足由使用方自行评估 |
| air gap／完全离线部署 | 适用于不能连外网的 AI 部署：技能包是单个归档，解包即用，示例与检查全在本地运行，不需要访问仓库或外部服务 | 需要目标机器已具备 Python 3 与 PyYAML；离线环境请提前备好这两个前提 |
| 内网/供应链受限 | 适用于只允许分发二进制归档的环境：可只给 `tar.gz` 与 `sha256`，不暴露源码仓库；安装前校验摘要 | 分发渠道与签名策略由使用方负责，本包不提供签名 |

以上均为**设计推断**；企业环境中的实际效果未验证。

## 安装与第一次使用

见 [PACKAGING.md](PACKAGING.md)：下载 → 校验 → 解包 → 改名 → 放进 skills 目录 → 约定七项信息 → 拿一个真 bug 走一遍 → 对照「什么才算这轮成立」。

## 未验证清单

- 弱模型可用性：**未验证**（没有小参数模型证据）；
- 路由测试：仅同模型族自测，**非弱模型证据、不构成验收通过**；
- 企业合规：**未评估**，不声明满足任何标准；
- 真实仓库上的成功率：**未验证**（只在随包示例仓上跑通）；
- 「对强模型/弱模型有提升」：**不作为结论**，上文只写设计推断。

## 包里还有什么

- `SKILL.md`：技能入口与状态路由（模型按它决定下一步）；
- `stages/`：三份阶段说明（复现、定位修复、验证）；
- `schemas/`：四类交付物与卡点日志的格式；
- `validators/`：八项自动检查、一项人工清单、卡点日志检查；
- `examples/defect-repro-fix/`：一个可一条命令跑通的完整示例；
- `BACKFLOW.md`：卡点日志怎么汇总、谁分诊、版本怎么递增；
- `PACKAGING.md`：打包与安装说明。
