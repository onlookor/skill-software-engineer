# 回流流程：卡点日志怎么汇总、谁分诊、版本怎么递增

> 适用范围：`skills/software-engineering/` 这一套技能。日志形状见 [schemas/blocker-log.md](schemas/blocker-log.md)，打包见 [PACKAGING.md](PACKAGING.md)。
> 本流程只处理「卡点」，不处理需求、不做路线图；它不改变技能能执行哪些任务。

## 两条限制（先写在前面）

1. **未触发的情况，技能自身记不了。** 没被意识到、或答完了但答错的卡点不会留下记录。漏触发只能靠**部署侧会话记录**与**人工抽样审计**统计。**不得把「0 条漏触发」当作成绩**——0 条可能只说明没记录。
2. **卡点日志不改变技能能执行哪些任务，不属于任务交付物。** 它不是第五种交付物，不新增 stage、不放宽「明确不做」、不参与 V01–V09 判定。要改边界，只能走 `SKILL.md` 的「扩张锁定」四条，本条流程无权代劳。

## 角色

| 角色 | 是谁 |
|---|---|
| 记录人 | 部署侧实际使用技能的人（或其值班） |
| 人审人 | 部署侧的另一人（**不得是本次记录的被记录会话自身**） |
| 汇总人／分诊人 | 技能维护者（交付方） |
| 裁定人 | 人类（批准人字段新写一律 `onlookor`） |

## 六步流程

每步写：谁做 → 产出什么 → 什么条件下不得进入下一步。

### B0 采集（记录人）

- **谁**：记录人，在部署侧本地。
- **产出**：一条或数条 `blocker-log.yaml` 记录，严格按 schema 四类内容；默认**不上传**。
- **不得进入 B1**：记录里出现任何真实路径、仓库名、主机名、账号、内部地址或代码片段时，不得提交人审——先按 schema 重写成抽象描述，写不抽象就丢弃该条。

### B1 人审与脱敏（人审人）

- **谁**：部署侧的另一人。
- **产出**：机器校验通过（`check_blocker_log.py` 退出码 0）＋人读完确认无残留标识；决定「提交」或「不提交」。
- **不得进入 B2**：机器校验非 0；人审发现黑名单漏掉的不带点仓库名／主机名／账号；或记录明显编造、无法对应到一次真实卡点。**未过人审的记录不得进入任何汇总。**

### B2 汇总（汇总人）

- **谁**：技能维护者。
- **产出**：只含已过人审记录的汇总表，按 `(card_file, card_section, type)` 计数，附原始记录；表头必须标注「仅统计已提交记录，不代表漏触发为 0」。
- **不得进入 B3**：汇总中含未过人审的记录；记录缺 `skill_version` 或版本号无法对应已发布包；同一批记录被重复计入。

### B3 分诊（分诊人；越界时转裁定人）

- **谁**：技能维护者；涉及阶段、判定规则、交付物类型或「明确不做」的变化时，必须转人类裁定。
- **产出**：每条记录的处置结论，三选一——`改卡`（写明改哪个文件哪一节）、`不改`（写明理由）、`需人类裁定`（写明争点）。
- **不得进入 B4**：结论为 `需人类裁定` 尚未裁定；或处置方式实质上新增了 stage／交付物类型／放宽「明确不做」——那属于边界扩张，按 `SKILL.md`「扩张锁定」四条办，B3 不得直接改。

### B4 改卡与版本递增（维护者）

- **谁**：技能维护者。
- **产出**：改后的卡＋`SKILL.md` 的 `version` 递增＋按新版重打包。
- **版本规则**（`version` 以 `SKILL.md` frontmatter 为唯一来源，打包脚本读取它）：
  - **patch（X.Y.Z→X.Y.Z+1）**：只澄清表述、补例子、修错字，**不改任何判定**；
  - **minor（X.Y→X.Y+1.0）**：改门、改字段、改 validator 或新增校验项，但不新增交付物类型、不放宽「明确不做」；
  - **major（X→X+1.0.0）**：改变技能边界（新增交付物类型、放宽「明确不做」），**必须先有人类批准**，再按扩张锁定四条执行。
- **不得进入 B5**：判定变了但对应 validator 没改；或版本号没递增；或示例 `examples/defect-repro-fix/run.py` 未重跑通过（V01–V08 非全 pass）。

### B5 发布与回写（维护者，部署侧自愿升级）

- **谁**：维护者打包含发布；部署侧决定是否升级。
- **产出**：`dist/software-engineering-<version>.tar.gz`＋`.sha256`＋release 说明（写清本版改了什么卡、**明确不包含什么**）；本轮的卡点汇总与处置结论随版本归档。
- **不得进入 B6**：打包脚本的正向断言或反向断言失败；release 说明遗漏「不包含什么」；版本号与包名不一致。

### B6 周期性复核（裁定人）

- **谁**：人类。
- **产出**：抽样审计结论——从部署侧会话记录里抽样，估计漏触发与错答率；结论写进下一轮汇总的附注。
- **不得进入下一轮 B2**：把「本周期 0 条卡点」当作「本周期无卡点」；抽样未做就宣称漏触发为 0。

## 一图概括

```
部署侧：B0 采集 → B1 人审脱敏 ──(未过人审即止)──▶ 提交
                                                    │
交付侧：                          B2 汇总 → B3 分诊 → B4 改卡＋升版本 → B5 打包发布
                                                    │                        │
                                                    └──── 越界则转裁定人 ◀───┘
人类：                                     B6 周期抽样复核（估漏触发）
```

## 明确不做（本流程）

- 不把卡点日志变成任务交付物，不新增 stage，不参与 V01–V09；
- 不用「记录条数」或「0 条漏触发」评价技能质量；
- 不自动上传、不自动提交、不自动改卡；
- 不接管需求、路线图、发布计划。
