# validators：V01–V08 可执行、V09 人工

> 本目录校验的是**技能交付物**（`repro.md`、失败测试、`fix.patch`、`verify.log`），不是仓库内部产物；与 `registry/` 下的检查器不共享路径与命名，禁止混用。

## 用法

```bash
python3 validate.py --config <使用前配置快照.yaml>            # 跑 V01–V08 全部
python3 validate.py --config <使用前配置快照.yaml> --only V01 V02
```

- 配置快照七项（`repo_path`／`test_command`／`build_command`／`repro_runs`／`repro_timeout_seconds`／`allowed_scope`／`cache_cleanup_policy`）只从 `--config` 指向的文件读取，与 `SKILL.md` 的 `mount_declarations` 一一对应。**本目录不含任何项的值、默认值、示例值、推荐值。**
- 快照可另带元数据 `agreed_at`（ISO-8601）与 `agreed_by`（恰好两项非空身份）。它们不属于七项、不参与缺项判定；给出时校验格式，其它未声明键判非法。
- 缺任一项 → 退出码 3，不静默通过。前六项由自动检查直接使用或核对；`build_command` 只校验类型与单行，**V01–V08 不执行构建**（交付物不依赖构建，执行构建只引入副作用与超时），因此不设 `build_not_configured` 状态。`cache_cleanup_policy` 只判存在、类型与非空，策略是否足以排除缓存与构建产物复用只能由人判断。
- 复现命令与测试命令只接受字面量 `python3 -I <仓内相对路径>`（恰好三个词；`python3.14`、`./python3`、`python` 别名一律拒绝）：不接受 `bash x.sh`、`env VAR=1 …`、赋值前缀、`-m`／`-c`、参数与复合命令。执行时清空全部 `PYTHON*` 环境变量、以隔离模式运行并按解析后的真实路径判定仓内，工作目录钉在仓根。`sitecustomize`／`usercustomize` 的屏蔽只作用于**被校验的父进程**；测试自己拉起的子进程另走覆盖率注入（S3 要求采集），两者不是同一条命令，也不矛盾。
- 交付物位置：`repro.md`、`localization.md`、`fix.patch`、`verify.log`、`fix-report.md` 在仓根；失败测试与元数据在 `tests/`。

## 退出码

`0`＝pass；`1`＝fail；`3`＝`cannot_evaluate`。三者之外无其它退出码。多项合跑时：任一 fail → 1；否则任一 cannot → 3；否则 0。

## 逐条：判什么／判不了什么

| ID | 类型 | 判什么 | 判不了什么 |
|---|---|---|---|
| V01 | schema | `repro.md` 十字段齐全、类型正确、`fingerprint.run1 == run2`；`observations` 非空且值为字面量（数字、字符串、`True/False/None`、字面量容器）；`under_test` 是 `module.func` 或 `module.Class.method`（可多个），**只接受点号函数或方法**（类、常量、模块名直接拒；源码定位不到时判 cannot）；`first_observed` 按 ISO-8601 校验，并接受 YAML 解析出的 `date`／`datetime` | 内容是否真实；`expected`／`actual` 是否忠于用户所述；声明的入口是否就是用户报障的入口 |
| V02 | 可执行命令 | 元数据 `file` 是仓内 `tests/` 相对路径且真实存在；复现命令是 `python3 -I <仓内相对路径>`、实际执行的脚本与 `file` 同一文件；**引导自己调用 `observe()` 并按 `repro.md.observations` 比较**，退出码非 0（可能是观测不一致，也可能是崩溃；V02 不消费分类标记）；输出非空；连跑 `repro_runs` 次摘要一致；声明摘要与实跑一致 | 该失败是否就是用户报的那个问题；摘要归一化是否覆盖全部噪声；失败是否由被测行为引起只能由 V08 的逐行覆盖证据判断（V08 只复跑同一命令，不是额外兜底） |
| V03 | 可执行命令 | 测试文件是仓内 `tests/` 相对路径（绝对路径、仓外路径、软链出仓均不合格）、存在、非空；**复现测试契约**：不调用任何断言 API（`assert`、`unittest` 整族、`self.assertEqual` 一律拒），模块级只允许导入、`sys.path` 设置与无参 `observe()` 定义，**`observe()` 的函数体只允许单条 `return`**（禁 `Assign`／`AugAssign`／`If`／`Try`／`Raise`／`With`／`For`／`While`／局部函数定义／局部重绑定；`type` 也在黑名单），返回字面量 dict 且键与 `observations` 一一对应，每个观测值必须**直接是声明入口的调用**（`f(...)`／`mod.f(...)`／`Cls(...).m(...)`；局部变量中转不算）；`single_run_command` 同样是白名单形式并真执行该测试；单独运行失败（由引导比对）；HEAD 与 `base_commit` 一致；仍禁止 `open`、读源码文本、`os`／`subprocess`／`importlib`／`io`／`codecs`／`pkgutil`／`runpy`／`operator` 等模块，`exec`／`eval`／`__import__`／`getattr`／`hasattr`／`vars`／`globals`，读写环境变量，给已导入对象的属性赋值（猴补丁），`sys.modules`，`__dict__`／`__globals__`／`__subclasses__` 等；也不得读取被测入口之外的属性（`calc.EXPECTED`、`add._se_fixed`） | 覆盖率；命令语义上是否真的只跑了该用例；观测输入与期望值的语义独立性（单条 `return` 只排除了函数体内自行比较与伪造，不证明输入选得对）；动态拼接属性名等极端绕法判不了（见「已知边界」） |
| V04 | 可执行命令 | `git apply --check` 通过 | 补丁语义是否正确；补丁是否最小 |
| V05 | 黑名单 | `touched_files ⊆ localization.md.files`，且 ⊆ `allowed_scope` | 声明范围本身是否完整（漏文件判不了） |
| V06 | 黑名单与最小性 | `tests/` 路径的已有文件被改写、被改名、被移出 `tests/` 都会拦（改名按 diff 的 a 侧旧路径判定）；`tests/` 内新增文件必须是 `repro_*`；**补丁执行时机**（AST，a 侧按 base、b 侧按补丁后源码）：普通函数／方法体内的改动放行；模块级声明式改动（`import`、模块常量、类属性／dataclass 默认值、模块级 `try/except` 内赋值、docstring、声明式装饰器、`def`／`class` 头）放行；改到模块级可执行语句（Expr 调用、属性目标猴补丁、控制流头）判 `cannot_evaluate`，并写明「该缺陷需要改模块级声明，超出本技能适用面」；`evidence_kind` 取值合法；`estimated_touched_files`／`estimated_diff_lines` 与实际补丁一致；`hypothesis` 下禁止「根因已确认／彻底修复／问题已解决」且 `status` 不得为 `fixed` | 只保护 `tests/` 路径名，不保护行为：`tests/` 之外的数据文件或夹具被改动不在本项覆盖范围；新增 repro 测试内部语义是否诚实（静态只判返回值形态）；预估数字是否诚实地反映设计意图（只判与实际是否一致）；结构规则只覆盖 `.py` 生产文件；导入期可达性不做语法推断——断言 API 在导入期被改写不影响判定，因为引导从不使用断言设施；AST 侧现存缺陷见仓根 `TECH-DEBT.md`（不随包分发） |
| V07 | 可执行命令 | 使用前 `test_command` 全绿 | 测试集本身是否足够；绿是否由本次补丁引起 |
| V08 | 可执行命令 | 三段顺序与退出码（非0／0／非0）；`patch_sha256` 与 `fix.patch` 一致；`test_command_used` 与使用前快照逐字一致；`commit` 与当前 HEAD 一致；已跟踪文件无未提交改动；**实际重跑三段**并与日志退出码逐段比对；复现测试同样过白名单与 `under_test` 入口限制；每次受控执行都做**采集入口完整性**比对（`trace`／`threading`/`sys.settrace`／`runpy.run_path`／`builtins` 执行入口／`sys.modules` 基线被替换且未复原即 cannot；自恢复与 `os._exit` 发现不了）；两态都在受控执行下采集覆盖行（含测试新建线程与其拉起的子进程），补丁在生产代码上删除/新增的行必须分别被 base／patched 的复现测试执行到，交集为空即 fail；**变异检验**：对补丁触及的生产代码新增行逐行造变异、对删除行做整块回退，重跑复现测试必须出现**观测值与期望值不一致**（引导在完成自身比对后写入 `stage=mismatch`；分类只认该标记，不认异常类名）；崩溃、超时、`SystemExit`／`os._exit` 等提前退出都不算杀死变异；全部存活或整份补丁造不出可编译变异即 fail；`fix-report.md.status=fixed` 直接 fail（V09 必须人工执行） | 缓存与构建产物是否真的被清理（重跑沿用同一环境，不能替代清理策略）；绿是否由本次补丁引起（靠第③段、覆盖交集与变异检验逼近，不绝对）；测试是否只跑了声明的那一个用例（只看该测试进程实际执行到的行）；测试自己伪造证据（见「已知边界」） |
| V09 | 人工清单 | 根因陈述与 `evidence_kind` 是否成立 | **只能人工执行**：没有任何字段能让它自动成立；`v09_signoff` 等仓内字段可由执行方书写，机器不采信为复核证据；见 [V09-checklist.md](V09-checklist.md) |

## 运行时机（状态相关，不是随便复跑）

| 项 | 应在何时跑 | 原因 |
|---|---|---|
| V01／V02／V03 | S1 写完交付物后、补丁前 | V03 要求 HEAD 等于 `base_commit` 且用例仍失败 |
| V04／V05／V06 | S2 写完 `fix.patch` 后、应用前 | `git apply --check` 要求补丁尚未应用 |
| V07 | S2 通过条件／S3 第②段 | 要求补丁已应用且全量测试绿 |
| V08 | S3 写完 `verify.log` 后 | 会实际重跑三段：要求补丁尚未应用、已跟踪文件干净；重跑后自动撤销补丁，不改动交付物 |

## 第③段（撤补丁复败）的证据有效性前提

第③段的结论只有在**排除缓存与构建产物复用**之后才可采信。若撤补丁后复现用例仍是**绿**的：

- 不得直接当成「补丁无效」，也不得把「三段日志已齐」当成任务完成；
- 必须先用使用前「缓存与构建产物清理策略」排除缓存与构建产物复用；
- 排除后仍绿，才是真的没有复败；仍绿时第③段退出码为 0，V08 会判 fail（期望非 0），不得改写退出码凑通过。

**实例（2026-11-16，随包示例仓实测）**：Python 撤补丁后复现用例仍绿，原因是 `__pycache__/calc.cpython-*.pyc` 复用了补丁态字节码。
- 触发条件：撤补丁后的源文件与补丁态在**同一秒内**被写入（pyc 头部记录秒级 mtime），且**字节长度相同**（如 `a - b` 与 `a + b`）；两项同时成立时 pyc 的 mtime＋size 校验通过，缓存被复用。
- 后果：第③段「撤补丁复败」假绿——三轮验证看似走完，实际没有复败；若把日志齐备当证据，就会把未验证的修复记成已修复。
- 处置：属使用前「缓存与构建产物清理策略」应覆盖的范围。自动检查不清理、也不判清理是否生效；只能由人核对 `test_command_used` 原文与清理策略后再采信第③段。

## 判不了就不判

- 任何一项缺输入或执行超时 → 退出码 3，不当作 pass，也不当作 fail。
- 不得用「都跑过了」代替「每条都判过」；`cannot_evaluate` 必须原样上报。

## 已知边界（天花板）

以下不是本轮要修的 bug，而是同进程证据的固有上限与当前实现的边界；文档与报告不得越过这些上限下结论。AST 侧的具体缺陷不在「已知边界」里一笔带过，单独记在仓根 `TECH-DEBT.md`（不随包分发），作为将来改版的工作项。

- **同进程证据可以被被测代码或生产补丁伪造。** 复现测试、生产补丁与覆盖率采集在同一进程树里运行。输出通道的 fd 号走环境变量 `SE_COV_FD`（不再放进 argv，测试也读不到 `/proc/self/cmdline` 里的路径），但进程仍能从 `/proc/self/environ` 读到 `SE_COV_FD`／`SE_COV_DIR`／`SE_COV_REPO`，往该 fd 写伪造的覆盖率 JSON，或用 `os._exit(0)` 跳过退出钩子与观测值比对。伪造不限于测试代码：生产补丁在导入期或运行时都能主动写 fd、改环境或提前退出；**没有完整的机械出口**，这是沙箱问题而不是校验器能单独解决的问题。
- **判定不经过任何断言设施，但仍不能证明整个进程未被篡改。** 引导自己调用无参 `observe()`、自己按规范化 JSON 比较并给出退出码，从不 `import unittest`，也不调用 `assert`／`TestCase` 的任何方法。因此「临时替换 `assertEqual` 再恢复」「改 `__code__`／`_baseAssertEqual`」「把 `unittest.TestCase` 整个类换掉」「在新建模块的导入期安装假断言」都不再影响判定——第八轮实测的这些绕法在新契约下被根除，而不是被完整性快照挡住。采集入口快照只覆盖 `trace`／`threading`/`sys.settrace`／`runpy.run_path`／`builtins` 执行入口与 `sys.modules` 基线，且只能发现「替换后不复原」；自恢复与提前退出发现不了。导入期副作用即使不碰这些对象，也仍可能改写被测行为本身——那属于行为是否正确的范围，由覆盖与变异检验逼近，不由完整性快照证明。
- **子进程覆盖不是全覆盖。** 只有继承环境、且未用 `-I`／`-S` 启动的子进程才会加载覆盖率注入点；测试显式清空环境或换解释器后拉起的子进程不会被采集。
- **变异检验只证明「测试对补丁行敏感」，不证明「期望值是对的」。** 期望值独立写在 `repro.md`，不再从被测代码取；但测试仍可能选用让 base 与 patched 都产生同一观测的输入，或用补丁新增的常量作为观测对象，使变异被「杀死」而 bug 原样未修。静态规则只判「返回值直接是入口调用」，判不了观测输入与期望值的语义独立性；这部分只能由人工 V09 复核。
- **`V01–V08` 全 pass 不等于修复成立。** 自动检查只说明交付物形状与受控执行证据自洽；根因是否真的成立、修复是否真的解决问题，必须由人按 V09 清单复核。V09 没有自动出口：`v09_signoff` 等仓内字段由执行方书写，不能作为复核成立的证据；`status: fixed` 会被 V08 直接拒绝。
- **M6 不由仓内文件判定。** `review/approval.md` 等仓内文件可由执行方书写，不能当人类批准门；机器只显示「未提供外部批准」。
