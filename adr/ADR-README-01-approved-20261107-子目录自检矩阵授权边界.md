## 1. 背景与问题

`registry/README.md` 是注册表的下游产物，但 §5 的检查矩阵与 seed 资格公式长期被当作规范权威引用。问题不是「README 是否可以在子目录」，而是两件事：

1. **制度安排**：子目录能否承载可执行自检矩阵？母本 L21 把 `README.md` 登记为「目录规约」，写明「变更纪律与自检矩阵见 `registry/README.md`」；`AGENTS.MD` L15 复述同一指针。这构成授权，但授权的**实质边界**从未写明。
2. **文本归属**：§5 的各项判据中，哪些是照抄、哪些是合法细化、哪些是纠偏、哪些是越权？不逐项拆解就无法追认。

本轮同时处理一处已确认的文本越权（C-ENV 行把适用对象收窄到 1.2.1/1.2.2/1.2.3），并把 C-ST 中一条无母本明文的附加子句改为由 M2 承担。回溯重判规则按**方案甲**定稿（§6），方案乙作为已否决备选保留。

### 3.2 追认对象

追认「`registry/README.md` §5 可作为母本 M 系列与 C 系列判据的**机器实现载体**」这一制度安排。追认范围包含：

- **承载位置**：矩阵与 seed 公式住在子目录，而非母本正文；
- **可执行化**：把母本分散条款转写为逐条矩阵、逐项检查与工具实现。

不包含：对 §5 每一句具体文本的认可。文本是否越权，按 §4／§5 逐项判断。

### 3.3 授权边界

「自检矩阵」的授权只覆盖**可执行化**，具体是四可、三不可：

| 可（授权内） | 不可（越权，须另证或另批） |
|---|---|
| 1. **列检查行**：把母本分散的判据归并为逐条矩阵 | 1. **新增义务**：母本无据的必填、禁止、资格条件 |
| 2. **照抄级别与量词**：`hard`／`soft`／`P2`、`∀E(status ≠ draft)` 等逐字承袭 | 2. **软硬互换**：软升硬、硬降软 |
| 3. **规定执行顺序**：矩阵行序与检查先后（不改变判据内容） | 3. **收窄或放宽适用对象**：如「全部 kind」缩到 1.2.1–1.2.3，或把 1.2.x 扩到全库 |
| 4. **规定诊断文案**：失败原因、跳过理由、报告格式 | — |

依据：0.13 L271（注册表条目新增/修改/删除一律完整 ADR）；0.17.4 L435（机器层字段变更＝完整 ADR）；changelog L585（「零新增规范命题」「只实现检查矩阵，不定义新规则」）；`ADR-STY-FIM-01-approved-20261107-框架内生元方法与source_class.md` §5.5（细则写 ADR、README 只留指引，避免形成第二个权威点）。

### 3.4 追认效力

- **制度安排可追认，文本越权不可追认**：本 ADR 追认承载位置与可执行化；对逐条判据的处理见 §4。
- **0.17.5 时期无独立 ADR，不倒查为程序违规**：当时不存在 `ADR-*.md` 文件形态；0.13 的「完整 ADR」实体要求以 changelog 长条＋母本修订落迹承载（`1b210b9` 的 changelog L577、L585 即为该形态）。本追认只及于制度安排，不及于任何具体越权文本。
- **`1b210b9` 同批事实**：README §5、母本 L21 授权、AGENTS.MD L15、根 README 目录行由**同一提交**写入，不存在「先授权、后加严」的时序。该事实如实记录；它说明这是**一次设立**，不说明文本天然正确。
- **追认不改变现行结果**：本轮改正前后 138 条均 138/138 过检，零翻转（§7）。

### 4.1 M9：纠偏，不是新增

0.17.7 L477 先写「准入检查全部机器可判定（M2–M6）」，随后列出**六项**：1→M2、2→M3、3→M4、4→M6、5→M5、6→组合关系闭合。第 6 项（L484）「compatibility 中引用的 peer_entry 全部存在」正是 0.17.8 L513 的 **M9**。

因此「M2–M6」是**缩略标签**，不是连续枚举：它覆盖六项，但数值区间漏掉了 M9。0.17.5 L451 沿用同一标签。README 把 M9 列入 seed 公式，是恢复 0.17.7 第 6 项的原意，**不是新增检查**。级别照 0.17.8 为硬。

### 4.2 C-ST(ii)：删除子句，由 M2 承担

用户所称 C-ST(ii)，指 README L516（改正前）的附加句：

> 「附加：条目所属 kind 的剖面若为 `draft`（`profiles.yaml`，适用性无据 → KP-G3），该条目**不得**声明 `seed`」

它在代码中对应 `check_cst` 的 (iii) 分支（`registry/scripts/project.py` L1225 起，改正前含 `elif prof_status.get(kind) == 'draft': rep.fail(...)`）。

**两条可选路径：**

| 路径 | 做法 | 评价 |
|---|---|---|
| A. ADR 补授权 | 保留子句，由本 ADR 明确授权「剖面 draft → 条目不得 seed」 | 可解释，但等于在子目录再立一条状态规则，需逐次裁量授权 |
| B. 删除子句，M2 承担 | 删除附加句；M2 遇 draft 剖面判「完备性不可判定 → 不成立」 | **采用**；见下述理由 |

**采用 B 的理由：**

1. **有母本依据，不新增义务**：0.17.8 M2 负责 `fields_complete(E, kind_profile(E.kind))`；0.17.2 L387 明确 M2 按 kind 剖面判定。剖面 `status=draft` 表示其必填面含 `undecided_fields`（`profiles.yaml` 头注 4、KP-G3），完备性不可判定；硬检查在三值语义下不能为真，即 M2 不成立。这是既有判据的语义结论，不是新义务。
2. **减少本地规范存量**：保留 A 会在子目录留下一条母本未写的状态规则；删除 B 后，seed 资格只剩「公式各项成立」一条路径。
3. **消除第三份拷贝**：同一事实已由 kind 级 `META` 检查（`project.py` L1220–L1223「剖面为 draft 但已有 N 条条目入库」）与 M2 覆盖；C-ST 再写一遍属重复。
4. **必须同时修实现，否则开天窗**：改正前 M2 对 draft 剖面记 `skip`（`ok=None`），`Report.status_of` 得 `–`；而 C-ST(i) 只把 `✗` 计为失败。若只删文本不改 M2，draft 剖面下的 seed 条目会**通过** seed 资格。故本轮把 M2 的 draft 剖面分支由 `skip` 改为 `fail`，由 C-ST(i) 经 `SEED_CHECKS` 捕获。

**落地改动：**

- README L516：删除附加句，改为「剖面 `draft` 的情形已由 M2「完备性不可判定即不成立」承担」；
- README L508：M2 行补「所属 kind 剖面 `status=draft` 时完备性不可判定 → M2 不成立」；
- `check_m2`（`project.py` L801–L825）：draft 剖面分支 `skip → fail`；
- `check_cst`（`project.py` L1226–L1252）：删除 (iii) 分支与 docstring 的 (iii)；
- `META` 检查保留（L1220–L1223），作为 kind 级事实登记。

**批准记录（2026-11-07，D5）：**

| 要素 | 内容 |
|---|---|
| 裁决 | **确认保留** `check_m2` 的 `skip → fail`，不回退；批准人为用户本人（2026-11-07 会话指示） |

### 4.3 C-ST(i)：合法细化，仅承担 seed 资格面

C-ST(i)（README L516 改正后保留部分）：「`status=seed` 必须全过硬检查；未过者必须为 `draft`」。

派生依据：

- 0.17.5 L451：`draft→seed` 的许可条件是「M2–M6 全过」，且「通道终止后此迁移关闭」——seed 只能是已通过者；
- 0.17.7 L477–486：准入（draft→active）同样以 M2–M6 为质量门；
- 0.17.8 M2–M9：硬项清单与量词。

因此「seed ⇒ 全过硬检查」是对上述许可条件的反向表述，属**合法细化**，不新增义务。

**范围限定**：本公式中的 C-ST 只承担 seed 资格面。`check_cst` 的非 seed 分支（`active`／`deprecated`／`retired`）已改为 info-only，不再判硬失败，处置见 §4.6。

### 4.4 M5 取软：母本内部冲突，另记待裁

- 0.17.5 L451：`draft→seed` 条件写作「**M2–M6 全过**」，按标签区间包含 M5；
- 0.17.8 L507：`M5: narrative_sync(...) —— 软（P2 抽查，积累升 P1）`。

二者就**同一迁移条件**给出不同级别。README L519 取「M5 为软，记警告不阻断」，相对 0.17.5 是**放宽**；但该放宽源自母本自身冲突，不是 README 单方越权。

**处置**：不归入 README 越权；不在本 ADR 内裁决。登记为待裁冲突，可选口径至少三种（供后续裁决，不在本轮选择）：

- 甲：`draft→seed` 也只要求 M5 软通过（README 现状）；
- 乙：`draft→seed` 要求 M5 硬通过，其余场景软；
- 丙：改写 0.17.5 的标签，明确其不包含 M5。

现状影响：138 条 M5 全部 `✓`，三种口径下均不产生翻转。

### 4.5 C-ID：补进公式，不是说明不列

**判断：应补进公式。** 依据三条，全部指向同一结论——README 是唯一缺口：

1. **台账已在案**：`method_registry.yaml` 的 `status_transitions` 首条（`ST-STY-01`，2026-09-18）`condition` 已逐字写明「seed 资格另含 M9 ∧ C-ENV ∧ C-ST ∧ **C-ID**（README §5…）」；
2. **代码已在案**：`project.py` 的 `SEED_CHECKS` 自设立即含 `C-ID`（`ENTRY_CHECKS` 与逐条矩阵同样含）；
3. **母本依据充分**：C-ID 校验 `entry_id` 唯一与格式、`kind ∈ 0.17.3` 封闭枚举、无与母本既有已发布引用冲突的重排（0.17.2 `entry_id` 字段、0.22 承诺一）。身份不成立则条目不可被选型/守护/编译消费，是**前置**而非普通判据。

故不存在「说明不列的理由」：唯一成立的理由是文本遗漏，补入属可执行化（D2「可」第 1、2 项），不是新增义务。

**落地：**

- README L519：公式补 `∧ C-ID`，并注明「C-ID 为注册表级身份前置，按全体条目判定，失败时仅阻断涉事 `entry_id`」；

- 不改 `check_cid` 行为；不改 `SEED_CHECKS` 成员。

**语义说明**：C-ID 的判定粒度与其余七项不同——它只对失败项逐条记 `✗`，另对全体条目发出一条 `全体条目` 的 `ok`（`check_cid`，`project.py` L1127–L1169）。因此逐条矩阵中 121/138 条 `status_of('C-ID') = '·'`（无个人记录），这与「未检查」不同，不构成 skip。公式中的 C-ID 只在**该条目自身**有 `✗` 记录时才判其 seed 资格不成立。

### 4.6 C-ST 非 seed 分支：移除，不单列

**判断：移除硬失败，README 不单列。** 归属与理由：

- **归属义务**：`active`／`deprecated`／`retired` 的资格由 **0.17.5 L443–451 状态迁移权限**与 **0.17.7 L477–486 准入面**管辖；`seed 资格公式`只回答「能否声明 `seed`」，不回答「其他状态是否合格」。原实现把「任一硬检查未过 → C-ST 硬失败」施加到非 seed 状态，母本无此通用义务。
- **原本就是重复**：非 seed 状态下的硬检查未过，底层 M2／M3／M4／M6／M9／C-ENV 已各自产生硬失败记录；C-ST 再记一条既不增加信息，又让「C-ST」在报告中同时表示两种不同义务，混淆 seed 资格与其他状态资格。
- **不单列的理由**：公式与实现的分叉来自「代码有、文本无」，消除分叉的最小改动是**让代码回到公式范围**，而不是给公式追加一条本不属于它的判据。若在 README 单列「非 seed 状态也须全过硬检查」，等于在子目录新增状态规则，触及 D2「不可」第 1 项。

**落地：**

- `project.py` L1249–L1252：非 seed 分支由 `rep.fail('C-ST', …)` 改为 `rep.add('C-ST', eid, 'info', True, 'status=…（资格判据见 0.17.5／0.17.7，非本工具静态自检面）' + 未过项提示)`；
- README L516：C-ST 行结尾注明「本检查只判 seed 资格；`active`／`deprecated`／`retired` 的资格由 0.17.5／0.17.7 管辖，工具只记 info、不判失败」；
- 不新增 README 行。

## 6. 回溯规则：方案甲定稿

母本与既有 ADR 均未规定「口径变更后，已声明 seed 的条目如何重判」。最近的两条相关程序都**不是**回溯重判：0.17.6(3) 是编译器就绪后的前向重验证；0.17.4 的完整 ADR 针对**字段**变更，不针对**判据/口径**变更。故此处构成真实空白。**2026-11-07 人类裁决：采纳方案甲；方案乙作为已否决备选保留（§6.6）。**

### 6.1 采纳结论

| 项 | 方案甲（采纳） |
|---|---|
| 一句话 | seed 资格口径变更生效后，对全部已声明 `seed` 的条目按新口径**全量重判**；不通过者退出 `seed`，逐条人类裁定 |
| 与方案乙的分界 | 乙不重判、只挂风险标记，等下一次触碰；甲在变更当次清算 |
| 本轮对现有数据 | 重判结果为空（138/138 双标准皆过），§6.5 为首条执行记录 |

### 6.2 触发条件

**什么算「seed 资格口径正式变更」**——满足任一即触发：

1. **新增检查项**：把新的检查加入 `SEED_CHECKS`，或在 §5 公式中新增合取项（如把 M5 由软改硬、新增 C-XXX）；
2. **改软硬**：任一公式项的 `hard`／`soft` 级别变化（含 M5 的最终裁决，§4.4）；
3. **改适用对象**：扩大或收窄任一项的 kind／状态／字段范围（如 C-ENV 的全 kind 与 1.2.x 之争、M2 的 `∀E(status≠draft)` 量词变动）；
4. **删除或新增公式项**：从 §5 公式删除一项、或把公式外的检查并入；
5. **判据语义变更**：实现层对同一检查的判定语义改变（如 M2 的 draft 剖面分支由 skip 改 fail，D5）——即使公式项未增删，只要同一条目在新口径下的判定可能不同，也算。

**不算变更**（不触发重判）：诊断文案、报告排版、执行顺序、检查函数内部重构且判定结果不变、纯文档错字。

**由谁认定**：仅**人类**（用户本人）认定；Agent 只能提议并备材（0.10 第一条），不得自行认定生效。

**以什么形式生效**：

1. **完整 ADR**（0.13 L271／0.17.4 L435 同型）：写明变更内容、母本依据或授权依据、影响面；
2. **README §5 diff**：公式与矩阵行的实际改动（含旧文本与新文本）；
3. **changelog 条目**：`软件工程元框架成文法-changlog.md` 记录（若变更源于母本修订，随母本批次；若仅子目录实现，记在注册表侧）；
4. **台账登记**：`method_registry.yaml` 顶层 `seed_rejudication` 追加本批次条目（字段见 §6.4）。

**生效时点**：ADR 状态为 `approved` 之日（以 ADR 头部「日期／批准」为准），不是改动写入工作区之日。

### 6.3 执行流程

| 步骤 | 要求 |
|---|---|
| **时限** | 口径变更生效日起 **1 个工作日内**完成全量重判。超期须在 `seed_rejudication` 写明原因与新的完成日 |
| **产出脚本** | `registry/scripts/project.py`。以非写入式 `run_checks()` 计算（或 `--check` 写投影，但重判清单本身由独立快照比对产出，不依赖投影文本） |
| **重判清单** | 对**全部** `status=seed` 条目逐条计算新口径下的 `SEED_CHECKS` 结果；同时保留变更前快照（上一版 `project.py`＋上一版口径），逐条比较 `Report.status_of(entry_id, check)`，任何 `✓／–／· → ✗` 或 `✗ → 其他` 的差异均入清单 |
| **不通过者处置** | ① 回归 `draft`（`status: draft`）；② 在 `seed_rejudication` 登记差异字段；③ **须人类逐条裁定**——因为 0.17.5 L443–451 的迁移表**没有** `seed→draft` 常规迁移，回落只能逐条批准；④ 裁定结果二选一：口径差异（条目本身合规，按新口径补正后重新申请 seed）或条目缺陷（修正条目或申请 Waiver） |
| **重判清单为空时** | 仍须留执行记录（批次号、日期、口径版本、结果「空」），不得因空而省略 |

**为什么必须人类逐条裁定**：重判会把「声明合法」的条目变成「声明非法」。自动化只能给出差异，不能替人类判断差异属于口径演进还是条目缺陷；且 `seed→draft` 不在 0.17.5 的常规迁移权限内，工具无权自行改写状态。
