## 1. 背景与立意

本项目要做的是**接地编译的软件工程元框架**，不是某个具体软件工程框架。它天生不携带真实项目／组织事实；具体框架要等问题空间与现状（事实）空间都被填充到一定程度才落地。因此，“缺真实数据”不能一律当成待补缺口，必须**自上而下先判断字段类型与空间归属是否放错**。

本 ADR 的结论：PRJ-001…PRJ-011 的 22 项 `delivery_space` **不是数据缺口，而是双重错误**：

1. **类型错误**：母本 0.17.2 @342 逐字为
   `delivery_space: [谓词]  // 交付空间能力前提（如：∃ on-call 能力；CI 成熟度 ≥ 级）`
   放进该槽的必须是**能力前提谓词**，不能是问句；
2. **空间归属错误**：22 项中 **14 项**问的是“是否已登记／是否已声明／是否可观测”，属**现状空间**事实；**8 项**才是交付能力前提（工具链、采集面、索引面、判定面等）。

支撑证据：新口径普查实测 **1480 处方括号 ＝ 事实 23 ＋ 槽 1457**；23 条事实中 22 条正是 PRJ-001…PRJ-011 各两条 `delivery_space[0..1]`，第 23 条为 DPS-004 `envelope.bound_expr`。旧口径把 **1457／1480＝98.4%** 的正常谓词槽误计为事实债，根因是 README §3.3 旧约定“方括号＝待勘察事实”与母本 @342“谓词列表”冲突。口径修正见 README §4.17（丙类工具改造，不改母本／条目）。

## 2. 判定规则（逐项可核）

| 判定 | 规则 | 处置槽 |
|---|---|---|
| 现状空间事实 | 断言“注册表／谓词／角色／接线状态**已经**存在、已声明、可查询、可观测” | `current_space`，写成陈述式谓词（不得带问号） |
| 交付空间能力前提 | 断言“本部署**具备**工具链、采集面、索引面、判定面等能力” | `delivery_space`，写成 `∃ …` 能力谓词 |
