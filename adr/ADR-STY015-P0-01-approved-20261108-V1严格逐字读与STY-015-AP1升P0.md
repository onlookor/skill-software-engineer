## 1. 背景与授权

- **起因**：`SO-4` 收口后遗留 MJ-4 三条 P0 复核（`STY-008-AP2`／`STY-009-AP2`／`STY-015-AP1`）。复核中发现判据面存在口径混用：MJ-4 原文与 `G-STY-4` 的 impact 均把「1.5 V 系列硬性质违例的直接来源」当作 P0 入口，而 V1 的逐字定义为 `¬∃ cycle(forbidden_dependency)`——它只判**环的存在性**，不判**单条边**。
- **授权**（人类责任方，2026-11-08，两条同时成立、不互为垫脚）：
  1. `STY-015-AP1` 由 P1 升 P0；其依据**不得援引 V1**。
  2. V1 口径按**严格逐字读**收口：单条禁止边穿透不是 V1 违例，V1 不构成三条中任何一条的升级依据；MJ-4 的 P0 判据须把 V1 摘出，改为「违反已登记禁止边即 P0」；`G-STY-4` 的冲突表述同批处理。
- **授权边界**：改判据条文属本次授权内（用户明示「别退化成在 ADR 里加注记」）；不改母本其他条款、不改状态机取值、不新增谓词名、不改 `SO-4.status`。

## 2. 口径原则（先定，再动其它）

**V1 逐字读**：母本第 1485 行

```text
V1  dependency_rule 的 forbidden 项不构成环      ¬∃ cycle(forbidden_dependency)
```

- **只认违例环**：V1 的判定对象是「由 forbidden 边构成的回路是否存在」，不是「某条 forbidden 边是否被走」。单条禁止边穿透 → `cycle` 不存在 → **V1 成立（无违例）**。
- **因此 V1 不能承载任何单边升级**：`STY-008-AP2`／`STY-009-AP2`／`STY-015-AP1` 三者若都靠 V1 升 P0，等价于把「任意单条禁止边」读成违例，与逐字定义冲突。
- **两者是两类对象**：
  - **环**：图论性质，判据是存在性（有环／无环），可判定面在图结构上；
  - **禁止边**：登记在案的边谓词实例（`dependency_rule(L1, L2, forbidden)` 的第 3 槽项），判据是该边是否被 `depends_on` 穿透，可判定面在登记表 + 实例事实。
- **P0 的第二路另行成立**：1.5 第 1474 行 `dependency_rule` 的行内登记面已列三族边界规则，其中第二族「模块化单体模块边界（仅上层依赖下层）」是**已登记在案的禁止边**；穿透它本身就是直接违例，与有没有形成环无关。

## 4. `STY-015-AP1` 升 P0

### 4.1 改动

| 字段 | 改前 | 改后 |
|---|---|---|
| `signal_level` | `P1` | `P0` |
| 注 | 「…1.5 未登记模块边界方向谓词（VG-03）→ 无 V1 可绑定，定 P1；若在 `dependency_rule` 登记模块间禁止穿透，则构成 V1 违例直接来源，升 P0」 | 「2026-11-08 由 P1 升 P0（ADR-STY015-P0-01）：1.5 第 1474 行第二族「模块化单体模块边界（仅上层依赖下层）」为已登记禁止边，穿越即直接违例 → 9.2.1 P0 第二路。依据不援引 V1：V1 只认违例环，单条穿透不是环」 |
| `formal_anchor` 的 V1 注 | 「模块边界可经 `boundary_type` + `dependency_rule` 登记 → V1 校验面（条件性）」 | 「→ V1（仅违例环）校验面；单条穿透的 P0 路径不在 V1」 |

`detection_predicate`、`description`、`constraints_imposed`、其余 `formal_anchor` 均不动。

### 4.2 依据（不援引 V1）

1. 母本 1.5 第 1474 行 `dependency_rule` 行内已登记三族边界规则，第二族为「模块化单体模块边界（仅上层依赖下层）」——这是**已登记在案的禁止边**。
2. `STY-015-AP1` 的检测对象正是「模块边界只在文档里，代码里随意穿透」，即该族禁止边被 `depends_on(c1, c2, call, ·)` 穿透且不经声明的边界契约。
3. 母本 9.2.1 改后的 P0 第二路覆盖该情形（§3.1），MJ-4 同口径（§3.2）。
4. **V1 不参与**：穿透单条边不构成环，V1 的 `¬∃ cycle(...)` 对该实例求值为真（无违例）。

### 4.3 为什么不是「三条都升」

逐条核对其余两条的检测式与登记面（结论见 §5）：只有第二族被消费。三族消费情况：

| 1.5 第 1474 行族 | 消费条目 | 是否构成 P0 |
|---|---|---|
| 单体内部（禁止反向依赖） | `STY-014-AP1` | **否**：其检测式含 `¬declared(boundary_type(...))`，前提是边界**未**声明 → 无已登记边可穿透 |
| 模块化单体模块边界（仅上层依赖下层） | `STY-015-AP1` | **是**：已登记禁止边被穿透 |
| 管道-过滤器不得绕过上下游直接读写数据源 | `STY-013-AP1` | **否**：其检测式不涉已登记禁止边 |

故 `STY-014-AP1`／`STY-013-AP1` 保留原 `signal_level`，本 ADR 不改。

## 5. `STY-009-AP2`／`STY-008-AP2` 维持 P1

两者在严格 V1 下**都不升**，且理由不同：

| 条目 | 现状 | 严格 V1 下不升的理由 | 另需的前置裁定 |
|---|---|---|---|
| `STY-009-AP2`（外层泄漏进内层） | `P1` | 检测式 `∃ c_in, c_out: [c_in 属内层] ∧ [c_out 属外层] ∧ depends_on(c_in, c_out, call, ·)` 不限定部署单元；1.5 三族登记面均以模块／部署边界为对象，**环是否落在同一部署单元内（即 V1 的图域是否覆盖进程内环）尚无裁定** → 既不能据 V1 升 P0，也无「已登记禁止边」可穿透 | 先裁定 V1 图域；再在 1.5 立环方向族 |
| `STY-008-AP2`（适配器泄漏进核心） | `P1` | 检测式 `∃ core, ext: [core 属业务核心] ∧ [ext 为外部技术设施] ∧ depends_on(core, ext, call, ·)`；**1.5 无端口方向族**（无 `dependency_rule` 登记端口方向），既不构成环，也无已登记禁止边 | 先补 1.5 端口方向族 |

- 两条的 `signal_level`、注、`formal_anchor` 均不动。
- `STY-009-AP1`／`STY-008-AP1` 不在本次复核范围（原 `SO-4` 只点名三条 AP2／AP1 中的特定项），亦不动。

## 6. `G-STY-4` 表述的处理

`G-STY-4` 的 `closure.basis`／`impact` 原文含「该违例即构成 V1 违例直接来源 → 按 MJ-4 判据升 P0」，与 V1 逐字读冲突。处理方式：**不改 gap 原文**（`statement`／`impact`／`route` 按 0.22 逐字保留），在 `closure` 下新增同级键 `correction_2026_11_08`：

| 字段 | 内容 |
|---|---|
| `subject` | impact／closure.basis 中「V1 违例直接来源」表述的口径更正 |
| `ruled_by` | 人类责任方（2026-11-08 批准本 ADR） |
| `before` | 相应 `dependency_rule` 一旦登记在案，该违例即构成 V1 违例直接来源 → 按 MJ-4 判据升 P0 |
| `after` | 该违例即构成「已登记禁止边被穿透」的直接违例 → 按 MJ-4 判据升 P0。V1 只认违例环，不承载单条禁止边的升级路径 |
| `scope` | 只限语义、不改 gap 原文；与 `before` 冲突处以本块为准 |
| `effect` | 三族中本批只有第二族被 `STY-015-AP1` 消费为 P0 依据；第一族／第三族无人消费 → 二者维持 P1，不得据此自动改级 |

**为什么是「加限定语义」而不是「修订原文」**：`G-STY-4` 已 `closed`，其 `preserved` 字段承诺原文逐字保留（0.22）；修订原文会使「已闭合」的登记面与既有引用产生不可对账的缝。限定块与 0.22 兼容，且 `effect` 字段直接阻断了「三族整体自动升 P0」的误读。

## 7. 严格逐字读的收口方案：收益与代价

### 7.1 收益

1. **口径唯一、不可外溢**：`¬∃ cycle` 与「禁止边」是两类对象，各自有独立的登记面与判定程序；不再存在「某条边算不算 V1 直接来源」的解释空间。
2. **阻断爬升路径**：若混用，任何单边违例都可借「V1 直接来源」爬进 P0——这会使 P0 集合随风格条目数线性膨胀，P1 失去存在意义（0.14 的分级设计即被架空）。
3. **V1 的可判定性保持在图论层面**：有环／无环是确定的图性质，不需要额外裁定「哪条边算直接来源」；判定成本与争议面都更低。
4. **P0 的第二路仍然可达**：模块穿透这类「无环但明确违规」的实例并不因此失去 P0，只是改由 9.2.1／MJ-4 的「已登记禁止边」路径承载。

### 7.2 代价

1. **单条违规失去 V1 自动来源**：单条模块穿透、单条反向依赖这类「没有形成环但明确违规」的实例，P0 判定不再有 V1 这条自动来源，只能靠条款自身的登记面（1.5 第 1474 行那三族）。登记面未覆盖的族（端口方向、环方向）就无法升 P0。
2. **`G-STY-4` 的既有表述要改，与已批准结论产生缝**：`G-STY-4` 于 2026-11-04 批准时写的是「即构成 V1 违例直接来源」。本次以 `correction_2026_11_08` 限定语义，等于承认当时表述不精确；虽然原文保留，但「已批准」与「已更正」并存需要在阅读时以更正块为准。
3. **`STY-015-AP1` 的 P0 只靠 1.5 那一行**：若第 1474 行第二族的登记面将来被改动（例如三族被重排、措辞被替换），`STY-015-AP1` 的 P0 依据会跟着动摇。这是「只靠登记面」结构的固有脆弱性，无法用注记消除。
4. **判定工作量转移**：从「图论判定」转移到「登记面核对」——每新增一族禁止边，都要显式登记并逐条重判受影响条目（C6.3 已把这一步写成义务）。

### 7.3 防止渗透的机制

机制不放在 ADR 注记里，而落在三处**判据文本面**：

| 层 | 落点 | 防什么 |
|---|---|---|
| 判定语义 | `CHECK-SPEC.md` **C2.4** | 把 P0 三路写死；明写 V1 只认违例环，单条禁止边不得经 V1 承载 |
| 判据条文 | `method_registry.yaml`: **MJ-4** | P0 集合中删去「V1 直接来源」；改「已登记禁止边被穿透」；环上的边按禁止边路径成 P0 |
| 变更纪律 | `CHECK-SPEC.md` **C6.3** | 禁止以注记／行内注／`narrative`／「按 G-STY-4 理解」把「禁止边」读回 V1；此类改动须走 0.13 完整 ADR＋逐条重判；仅改注记视为未生效 |
| 母本权威 | 9.2.1 第 3600 行 | 母本侧 P0 定义已含第二路，注册表无法单方面回退 |
| 批次先例 | `CHECK-SPEC.md` **C5.17** | 把本批结论固化为先例，下一次「顺手放宽」须先推翻先例并说明理由 |

M 系列断言：本轮**不新增**（M 系列是 0.17.8 的机器检查式，P0 分级不在 M 检查面内；为分级加 M 断言会越出 0.17.8 的封闭目录）。故防渗透落在上表五处，其中 C2.4／C6.3／MJ-4 是「条文级」，不是注记级。

### 7.4 被否方案

| 方案 | 内容 | 否决理由 |
