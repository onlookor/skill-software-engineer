## §2 现状核查

### §2.1 五槽原文与缺口

母本 5.2.6 @2514 逐字：

> `- [CFG-01] **配置 schema 注册**：全部行为相关配置项（开关、阈值、路由规则、池大小）登记入注册表：{键, 值域, 作用域, 级别, 生命周期}。`

五槽中：

| 槽 | 语义 | 能否表达「该条目是否仍生效」 |
|---|---|---|
| 键 | 配置项标识 | 否 |
| 值域 | 合法取值集合 | 否 |
| 作用域 | 生效环境／范围 | 否 |
| 级别 | `behavior｜parameter`（与 @2576 `flag` 第三槽同源） | 否（表达的是变更分级，不是条目存续） |
| 生命周期 | 审查期／到期日，实现为 `expiry` | 否（表达「何时该清理」，不是「现在是否有效」；超期只是 P2 漂移信号） |

结论：**没有任何字段回答「这条登记还在不在用」**。一个键可以已下线、已弃用、已被替代，但注册表仍只有「键＋值域＋作用域＋级别＋到期日」，机器无法区分 `active` 与 `retired`。

### §2.2 「生命周期」是什么（已核对原文，不是条目状态）

- @2516 逐字：`每个行为级开关诞生即带审查期/到期日（expiry 字段）；到期未清理 → P2 漂移信号（僵尸开关 = 隐式架构分支，腐化源）… expiry 载体＝本注册表条目字段；审查期基准＝开关生效之日起算，长度按影响级别取登记值。`
- @2576：`flag(G, scope, level, expiry)` —— `flag` 四槽，第四槽即 expiry。
- @2581：`expiry_of(gate)` —— 开关到期时刻（term function；与 `flag` 第四槽 `expiry` 区分，防槽名充谓词）。
- @2600 Z6：`∀ flag(G,_,behavior,_): ∃ approved(ADR(G)) ∧ declared(expiry(G)) ∧ now ≤ expiry(G) ∨ cleanup_filed`

即：`expiry` 是**值级时间点**（这个开关／这条登记何时到期），它的载体是注册表条目字段；Z6 用 `declared`／`now ≤ expiry`／`cleanup_filed` 判「有没有按时声明与清理」。**它不承载条目的存续状态**——到期未清理是「该清理而未清理」的漂移信号，不等于「该条目已失效」。

### §2.3 为什么这件事挡住了机械判定

[编译规范.md](file:///home/wgz/projects/skills/software-engineering/编译规范.md#L199) 2.3(a) 对 `registered(C)` 的可求值判据只覆盖两类对象：

> `对象在对应注册表存在且处于可消费状态（契约 lifecycle_state=published；注册表条目 status ∈ {active, seed}，seed 限 bootstrap 期）`

配置项既不是契约、也不是 0.17.2 的方法注册表条目 → `registered(键)` 落在 2.3(a) 覆盖之外，**不可求值**。这正是本批把 4 条 AP 降为事实槽的直接原因：

| AP | 位置 | 现写法 |
|---|---|---|
| CFG-001 AP1 | `method_registry.yaml` @7067 | `∃ 键: [行为相关配置项](键) ∧ ¬[该键已登记入配置注册表](键)` |
| CFG-001 AP2 | @7071 | `∃ 键: [该键已登记入配置注册表](键) ∧ ¬[五槽齐备](键)` |
| CFG-001 AP5 | @7083 | `∃ 键: [该键已登记入配置注册表](键) ∧ [同键多形态并存](键) ∧ ¬[取值有唯一真相源](键)` |
| VFM-001 AP4 | @9115 | `∃ 项: [该项为运行时生效的配置项](项) ∧ ¬[该项已登记入配置注册表](项)` |

## §3 候选方案

### 方案 A（推荐）：@2514 加第六槽 `status`

改法（已按读法 iii 落地，一次性行内改写，0 行增删）：

> `…登记入注册表：{键, 值域, 作用域, 级别, 生命周期, status}。`status` 与 0.17.2 条目 `status` **同一词汇表**（不另立枚举）；配置项只启用 `seed`／`active`／`retired` 三值（`draft`／`deprecated` 不适用于配置项）：`seed`＝已登记、未验证，`active`＝仍生效，`retired`＝已下线且禁止新增引用。可消费状态按《编译规范》2.3(a) 取 `{active, seed}`（seed 限 bootstrap 期）。`生命周期` 的 `expiry` 语义不变（值为到期日，见 CFG-03）。`

要点：
- **同一词汇表**：`status` 的可用值全部来自 0.17.2 的条目状态枚举，本表只做「配置项启用哪几值」的用法限制，**不新增任何枚举值**；不引入 `lifecycle_state` 别名，避免与契约面混。
- `draft`／`deprecated` 不适用于配置项：配置项没有「骨架登记」阶段（无 0.17.6 人工种子通道），退出即下线，不走「仍可读但禁止新增引用」。
- 可消费状态按 2.3(a) 取 `{active, seed}`（seed 限 bootstrap 期），与方法条目共用同一条消费判据。
- `expiry` 链条一字不动：`flag` 四槽、`expiry_of`、Z6 全部保持。
- 不新增谓词（不写 `status(键, 状态)`），`registered` 仍为 `arity: 1` 的公式约定词。

### 方案 B：把「生命周期」重定义为条目状态

改法：@2514 的「生命周期」直接读作条目状态（active／deprecated／retired），`expiry` 另行安置（新增一槽或降为附项）。

要点与代价：
- 这是**语义迁移**，不是加字段：@2516 明写 `expiry` 载体＝本注册表条目字段，一旦「生命周期」改指状态，`expiry` 立刻失去落点 → 必须同时改 @2516，并为 `expiry` 新开一槽（等于又回到六槽，只是名字换了）。
- 下游全链条要跟着改：@2576 `flag` 第四槽、@2581 `expiry_of`、@2600 Z6 的三支判据，以及数据侧 3 条 `expiry_of` 用法与 10 条相关条目。
- 收益与 A 相同（都能表达存续状态），代价高一个量级。

### 方案 C：不改母本，靠外部注册面承担（维持 C-18 现状）

改法：不碰 @2514；需要 `status` 时由项目侧／工具侧自行维护一份「配置项清单」，母本不认这个字段。

要点与代价：
- 母本零改动，短期零成本；4 条 AP 维持事实槽，判定责任永久回人工。
- 任何在 `registry/` 内自建 `status` 字段都会被判为「新增母本义务」（DATA-SPEC D1 开篇原则：本文只把母本既有义务落到数据面，不新增母本义务）→ 只能停在项目侧，**不能进入权威注册面**。
- 等于承认 C-18 永久开放。

## §5 结论与推荐

**采纳方案 A（读法 iii）**，理由按「改动面／可逆性／判定收益」三项：

1. **改动面最小**：母本只动 @2514 一行，`expiry`／`flag`／`expiry_of`／Z6 一字不改；`expiry_of` 3 条数据用法零改动。
2. **可逆**：加槽是可回退的增量；重定义（B）是语义迁移，回退要再改 5 处母本。
3. **判定收益完整**：C-18 闭合后，`registered(键)` 获得 2.3(a) 的第三类对象判据，4 条 AP 可回到机械可判；S-12／M2 均无连带成本。

**批准后的落地顺序（每步各自走变更权，不合并）**：

1. 母本 @2514 加 `status` 与取值语义（单独立 ADR，母本 1 行内改写）；
2. 编译规范 2.3(a) 增配置项对象类（`status=active` 可消费）；DATA-SPEC D3.4 同款注；
3. DATA-SPEC 附录 C.2 的 C-18 闭合（5→4），共同结论改「建表／补字段」措辞；
4. CFG-001 的 3 条 AP 与 VFM-001 AP4 恢复 `registered`——**先 info 干跑、硬 0 后再转 hard**，并复核 R2／M4 与 2.3 准入；
5. 同步 `[五槽齐备]` → `[六槽齐备]`（CFG-001 AP2 及其注释、CFG-002 的 applicability 引用、VFM-004 envelope），历史 ADR／changelog 按 0.22 不改。

**明确不做**：

- 不改 `0.17.2` 方法条目 schema（配置项字段不是方法字段）；
- 不新增 `status(...)`／`lifecycle_state(...)` 谓词，不扩 M4 词表；
- 不把 `expiry` 改名为 `lifecycle_state`，不重定义「生命周期」；
- 不在本提案中改母本任何一行；不预写第 4 步的数据改写。
