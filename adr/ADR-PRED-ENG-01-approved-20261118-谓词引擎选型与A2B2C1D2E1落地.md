## 1. 背景与问题

软工的谓词化停在“语法与登记”层，没有进入“求值”层：

- 词表在册 220 名（`predicates` 159 + `formula_words` 7 + `clause_defined_predicates` 54），条目字段只有 `name`／`arity`／`kind`／`source`，无类型、无可求值定义、无求值规则；
- `编译规范.md` 528–566 的 T1–T5 是纯文字规程，没有对应的执行实现；
- 14 张卡带 `step_id: S6`，4 张躯干卡没有；14 张卡的 `predicate_writes` 去重为 33 个谓词名；
- `gen_cards.py:405–409` 只生成字面字符串，`check-card.py:129–145` 只用正则抽名字，`registry/checks/m.py:72/83` 只查非空；全仓无解析器与求值器；
- `5.7` 只定义 `style` 投影，其余 7 类 `predicate_writes` 无投影规则；
- 三空间 `applicability` 只做形态校验（`project.py:1588–1674`）；
- 全仓 `.py` 内 `10.2.3bis`／`谓词化` 零命中。

外部审计（PM 项目对软工的谓词化审计）把这一状态登记为 `TD-SE-PRED-001`，并指出软工的教训是“有语法、没求值”。软工方向已由人类裁定为**造谓词引擎**，不采用“只做可求值子集、其余登记为代理或人工判定”那条路。

## 2. 决定

1. **造谓词引擎**：为设计谓词建立“解析—类型／arity／词项闭包—三值求值—finding”的最小闭环，覆盖卡片 `predicate_writes` 与 S6，不覆盖三空间 `applicability`（延后，见 `TD-SE-PRED-002`）。
2. **选型为 A2+B2+C1+D2+E1**：
   - **A2 受限表达式 DSL**：2.3 BNF 子集（原子、`¬`、`∧`、`∨`、`→`、有限域 `∀/∃`、比较、枚举、集合成员、引用核对）；不做递归、函数定义、开放世界推理。
   - **B2 三值语义**：`true`／`false`／`unknown`，Kleene 传播；`cannot_evaluate` 与 `fail` 分开；unknown 附勘察义务与 finding 来源。
   - **C1 手写 AST 解释器**：零第三方依赖；不用代码生成，不引入 Datalog／z3／Rego／CEL。
   - **D2 33 个卡片谓词名全覆盖**：`style` 作为第一个垂直切片；覆盖 14 张有 S6 的卡；四张躯干卡走显式豁免。
   - **E1 独立引擎模块**：`predicate_engine` 库，由 `check-card.py`／编译流水线／FVR 调用；`validate.py` 的 V01–V09 **不调用**引擎。
3. **不造通用谓词逻辑引擎**：不引入外部求解器，不做整层规则谓词化，不做运行期自然语言翻译；T1 的翻译仍是编写期一次性资产。
4. **设计与实现分离**：设计文档随 P0 同步成稿、每标一批黄金样本回改一次定义、P0 通过时冻结；**冻结之后才允许写 AST 与求值器实现**。P0 未过时保持 draft，不得用“先写实现再倒推定义”绕过。

## 3. 各轴选项与否决理由

| 轴 | 采纳 | 被否决选项 | 否决理由 |
|---|---|---|---|
| 载体与语法 | **A2 受限表达式 DSL** | A1 结构化字段 | 无法表达 33 名里已有的复合谓词，只能不断造新名，词表继续膨胀；复合语义仍无处安放 |
|  |  | A3 受限 Python 子集 | 可伪造面最大（`getattr`／builtins／推导式／lambda）；沙箱与版本漂移不可控；代码成为规范后不可审计、难迁回 DSL |
| 求值语义 | **B2 三值** | B1 二值 | 缺事实时必然外挂 `cannot_evaluate`，等于把三值藏在带外；与 0.18“未知 ≠ 假”、5.7 P3 冲突；静默排除候选 |
| 求值器形态 | **C1 手写 AST 解释器** | C2 受限 AST 转译执行 | 生成代码注入与漂移；栈轨迹与谓词不对应；不可审计；把“可审计”换成“少写解释器”不划算 |
|  |  | C3 现成约束／规则引擎 | 与零依赖纪律冲突；引擎模型不是本仓的三值＋finding 模型；依赖锁定与升级维护成本高 |
| 接线范围 | **D2 33 名全覆盖** | D1 只做 `style` | 30/33 名未覆盖；容易制造“已覆盖”的假象；无法回应审计的 33 名口径 |
|  |  | D3 连三空间 `applicability` | 对象是方法注册表、项目事实与开放世界输入，与卡片写入面不是同一事实面；会拖垮第一版；已登记为 `TD-SE-PRED-002` |
| 判定链接缝 | **E1 独立引擎模块** | E2 嵌进 `check-card.py` | 卡片检查器变成生产引擎；pilot 脚本膨胀；难单测 |
|  |  | E3 嵌进 `validate.py` | `validate.py` 判的是技能包复现测试是否可信，与设计谓词是否可求值不是同一对象；混进去会稀释 V01–V09，且它是分发面 |

**A2 的边界**：只做布尔组合、比较、枚举、集合成员、引用核对与有限域量化；不做递归、函数定义、聚合、时间推理、开放世界假设。

## 4. 不可逆点

| 不可逆点 | 为什么不可逆 | 必须定死的时间点 |
|---|---|---|
| AST／语法与词项闭包 | 33 名与检查器一旦依赖，改语法就是破坏性变更 | 设计文档冻结前（P0 通过时） |
| 二值／三值语义契约 | 下游 finding、FVR、报告都按它解释；后加 unknown 是语义变更 | 设计文档冻结前 |
| finding schema 与引擎 API | `check-card.py`／编译／FVR 一旦接入，改字段要全链迁移 | E1 接入前 |
| 33 名与卡片 schema | 改名／改 arity 要重迁 14 卡 | D2 开工前 |
| Python 子集（A3） | 代码成为规范，迁回 DSL 成本极高 | 本 ADR 已否决；若将来重提，须先立新 ADR |
| 外部引擎依赖（C3） | 版本／打包／语义锁定 | 本 ADR 已否决；若将来重提，须先立新 ADR |

**可逆或可延后**：三空间 `applicability`（D3）是加法，不改变已覆盖的 33 名；全 220 名求值、跨方面合并、多写者、性能／UI 都可后置。

## 5. 与 PM `ADR-0022` 的分歧处理

PM `ADR-0022` 的标题是“谓词化只做检查层”，其决定 1 说“不做整层谓词化”，决定 5 把“受限谓词 DSL + 求值器”列为唯一合理的中期扩展，决定 9 排在 P2。分歧不在“是否造引擎”，而在两条边界：

1. **“不造引擎”指不造通用／整层引擎**：本 ADR 同样不造 z3／Rego／CEL 式的通用引擎，也不做整层规则谓词化；只做受限 DSL＋求值器。这与 PM 决定 5 同向。**注**：“不造谓词引擎”是审计对 PM 立场的转述，不是 PM `ADR-0022` 的原话；PM 原文是“不做整层谓词化”。
2. **“schema + Python 足够”只适用于 PM 的检查层**：PM 的对象是 17 个 `check_id`／41 条 A.2 子句，判定面主要是工件 schema 与具名 Python 算子；软工的对象是 220 个谓词名跨设计事实（`selection_context`、`verdict_table`、`step_log`、`exclusion_record` 等），没有等价工件 schema 可以替代表达式求值。软工照抄会把“有语法、没求值”的教训再演一遍。

**从 PM 与审计借用的四条**（不涉及“不做引擎”）：

1. 语法与翻译分离：解析／arity／类型／枚举／引用闭包／三值求值由确定性程序做；翻译只在编写期，运行期不设翻译位置（PM 决定 2；`AUDIT.md` §9.1）。
2. 词项闭集：谓词名、关系词、枚举值、字段名必须来自登记表；未登记词项在编写期拒绝（PM 决定 4；`AUDIT.md` §9.1）。
3. 权威方向不改：判定以形式层为准，文本以母本为准；谓词通过不等于母本正确，形式缺陷不否定条文效力（0.24.3(3)；PM 决定 6；`AUDIT.md` §9.1）。
4. 单写者快照：先做单写者白板快照与比对；多写者合并、并发冲突不在当前范围（`AUDIT.md` §9.1；PM `ADR-0022` 未单列此条）。
