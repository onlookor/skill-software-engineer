# ADR-SRC-P0-09：背景守卫移出检测式（23 条 `registry_entry` 恒真合取项清理）

- 编号：`ADR-SRC-P0-09`
- 状态：approved
- 批准日期：2026-11-08
- 影响范围：`registry/method_registry.yaml`（23 条 `detection_predicate`）、`registry/DATA-SPEC.md`（新增 D3.9）、`registry/CHECK-SPEC.md`（C5.21 追加口径）、`registry/projections/*`（重生成）
- 不改：母本（0 行）、`predicate_vocabulary.yaml`（零 diff，`arity` 不动）、任何 Waiver／白名单／例外

## §1 授权与范围

用户 2026-11-08 指示：继续收口 S-12 收尾时自标的两处敞口；第一处优先——23 条 `registry_entry(VFM-00x, ·, ·, ·, ·, ·)` 的绑定敞口。要求先判定该子式在 detection 中承担什么，再按判定选路：

1. **背景条件**（反模式定义本身在册，与个体无关）→ 移出 detection，交给注册表侧静态检查，并说明谁接管；
2. **个体已登记** → 改绑 `∃` 见证，并按母本条款选 `registered(x)` 或 `registry_entry(…)`；
3. 确实无法脱离「条目在册」且现有检查已覆盖 → 保留，但在规范里定清「背景条件」的写法与标记。

边界：不改判定语义、不新增谓词的机械修正可直接落地；需新增谓词或改变判定含义的，先给方案停下。本 ADR 只处理第一处（背景守卫），第二处（72 处无 arity）另案报方案。

## §2 判定结论

**23 条全部属于第 1 类：背景条件（恒真守卫），不是「个体已登记」。处置＝移出 detection，由注册表侧静态检查接管。**

三条判据逐条核过：

1. **被约束对象与守卫主语不同**：23 条的形态统一为 `∃ <见证>: registry_entry(VFM-00x, …) ∧ [<见证的性质>](见证) ∧ …`。`registry_entry` 的主语是**方法注册表条目 VFM-00x**，见证是性质／检查／节点／结论／证据／模型／计划项／用例／契约／行为模式／评审点／告警／部署策略／信号——两者无变量共享。
2. **守卫在评估域内恒真**：`VFM-001…006` 是框架自带的 6 个 seed 条目（`profiles.yaml` 的 `seed_source.entry_id_range = VFM-001…VFM-006`）；detection 在已装载的方法注册表上求值，`registry_entry(VFM-00x, ·, ·, ·, ·, ·)` 不会为假，也不随见证取值变化。它不增加任何约束力。
3. **「个体已登记」另有正主**：母本对应语义由 `registered(x)` 承担（编译规范 2.3 内建语义：对象在对应注册表存在且处于可消费状态）。23 条中已有 4 条（VFM-001-AP4、VFM-004-AP2、VFM-005-AP3、VFM-006-AP4）直接写了 `registered(见证)`；其余条目的方括号条件已逐字写明「已登记硬性质／已登记发布节点／已登记为适应度函数」等。把 `registry_entry(VFM-00x, …)` 改绑见证既无母本依据，也会与 `registered` 的语义强度冲突。

**不是族级存在断言**：`VFM-00x` 是 `entry_id`（条目 ID），不是 `kind`（kind 为 `VFM`）。若作者本意是「VFM 族 6 条全部存在」，应写 `registry_entry(·, VFM, …)`（kind 槽）或独立检查，而不是把 6 个 ID 分别塞进 23 条检测式。该族级事实已由 META 的 seed 覆盖核对承担（§4）。

## §4 处置与接管者

**处置**：从 23 条 `detection_predicate` 中删除首个合取项 `registry_entry(VFM-00x, ·, ·, ·, ·, ·) ∧ `，其余部分逐字不动。新增规范 D3.9，明令背景守卫不得进入检测式。

**接管者（均为既有静态检查，无新增）**：

| 事实 | 接管检查 | 依据 |
|---|---|---|
| 条目 ID 存在、格式、唯一、kind 前缀 | **C-ID** | `project.py` `check_cid`（@1444–1486）；`{kind}-{三位序号}` |
| 条目 schema、字段完备、包络 | **M2** | `project.py` `check_m2`（@1098） |
| 17 个 kind 剖面齐备、`describes_kind` 合法 | **C-KP** | `project.py` `check_ckp`（@656–680） |
| VFM 族覆盖宣称：`8.2.1（6 行）` vs `8.2.1-T-01…06` 的 row_id 分布 | **META** | `project.py` @1506–1530；`profiles.yaml` @500 |
| 谓词名在册（含 `registry_entry`） | **M4** | `project.py` `check_m4` |

因此删除守卫不产生「无人接管」的空洞：族级存在与条目完备仍在 META／C-KP／M2／C-ID 的硬判据内。

## §5 语义影响

- **正常域（VFM-001…006 在册）**：23 条的真值表与删除前**逐点相同**。守卫是恒真合取项，删除不改变任何见证下的判定结果。
- **破坏域（假定 VFM-00x 不在册）**：旧式恒假（反模式永不触发）；新式仍可随见证性质触发。该域不可达——META 的 `8.2.1（6 行）` 核对会先硬失败。故**不构成判定含义变更**；ADR 中记明「真值不变式 = VFM-001…006 在册，由 META 承担」。
- **S-12 计数**：调用 501→478（anti_patterns 470→447）；variadic 23→0；无调用串 870→881。这是删除 23 次调用后的账面变化，不是豁免。
- **未覆盖 72 处**：不变（第二处敞口另案）。

## §8 被否方案

| 方案 | 内容 | 否决理由 |
|---|---|---|
| A | 保留守卫，规范里定义「背景条件」标记（如 `scope(VFM-001)`） | 恒真项继续占位，读者仍以为它约束见证；且要新造标记语法，S-12 还要为它开例外 |
| B | 改绑见证：`∃ 性质: registry_entry(性质, VFM, …)` | 见证多为性质／检查／节点等，不是方法注册表条目；`registry_entry` 的 E 槽语义不符，属错类型 |
| C | 改绑见证：`registered(见证)` | 语义上可行，但 4 条已有 `registered`、其余条目的方括号已逐字写明「已登记」；全量替换会重复约束并与 `registered` 强度混淆。仅作为**可选强化**留给后续谓词面治理，不在本批做 |
| D | 新增族级谓词（如 `family_complete(VFM)`） | 族级事实已由 META／C-KP 承担；重复造消费者违反「已有消费者不重复造」 |
| E | 用 `·` 填满槽位继续保留（上一批形态） | 形式合法但语义空转；正是本轮要收口的敞口 |

## §9 盲点

1. **D3.9 无机器判据**：本轮只做规范禁止＋存量清理，未加「检测式含自身 ID 守卫即失败」的检查。若后续回潮，靠评审发现；如需机器化，应作为独立子检查另案登记（不塞进 S-12）。
2. **`registered` 的强度未被本批统一**：本批未把其余 19 条改写成 `registered(见证)`；「已登记」究竟是 `registered` 还是方括号条件，仍在数据侧混用。
3. **不变式依赖 META**：若未来 `profiles.yaml` 的 `table_rows` 不再给逐表行数，META 会退化为 `info=None`，族级存在将失去机器消费者；届时 D3.9 的「谁接管」需要重新审。
4. **VFM-006-AP1 未纳入**：它用 `quality_impact_card(模式, ·)` 作为个体谓词，不是背景守卫；本轮不动。
5. **删除后 `registry_entry` 在四个检测面内出现 0 次**：谓词本身仍在册、仍在母本 @493 定义，合法；但 S-12 的 variadic 分支从此无真实样本，variadic 判定只剩单元测试覆盖。
