# 草案：CT-PACT-BACKEND-01 契约兼容策略（2026-11-14）

> 状态：**候选三已由人类选定（2026-11-14）**，本文保留三种候选的对比与放弃理由。
> 尚未写入 `pact-dsh` 仓库、尚未填白板 `compat_policy`、ADR 仍待批准（见同目录 ADR 草案）。
> 用途：作为 ADR（对应 X5）与白板登记（对应 X2）、契约测试（对应 T6）的上游依据。
> 事实基线：契约 `CT-PACT-BACKEND-01`，provider `pact-backend`，consumer `loop-core`，
> `lifecycle: published`，契约版本 `0.1.2`，包版本 `0.1.2`（已发布 npm）。
> 契约面（README 与 `src/pact-backend.js`）：`enabled/gates/status/seed/produce/consume/close`
> 七个方法；`FakePactBackend` 与 `WasmPactBackend` 同形实现。
> 现状：`compat_policy: null`（X2 fail）；无 ADR（X5 fail）；`contract_tests: []`（T6 fail）。

## 候选一：严格语义化（strict semver）

**内容要点**

- 契约版本与包版本同号，遵循 `MAJOR.MINOR.PATCH`。
- `PATCH`：只修实现缺陷，契约面不变。
- `MINOR`：**只增不删**——可新增可选方法/可选字段，不得改既有方法签名、错误码语义、返回结构。
- `MAJOR`：允许删除、重命名、改签名、改错误码；必须提供迁移说明。
- 0.x 阶段：`MINOR` 视为允许破坏，但**每次破坏都必须升 `MINOR` 并在 CHANGELOG 点名**。

**收益**

- 与 npm 生态习惯一致，消费者可用 `^0.1.2` 等常规范围表达预期。
- 判据清晰，T6 可直接把「只增不删」写成契约测试。
- 对 0.1.2 现有实现零改动：当前 API 就是基线，声明即成立。

**代价**

- 0.x 语义本身有歧义（npm 认为 0.x 的 minor 可破坏），需要额外写明本仓的解释，否则读者各取所需。
- 一旦发布 1.0.0，删除任何方法都要等 major，维护成本最高。
- 对早期快速迭代的约束最强。

**对 X2／X5／T6 的影响**

- X2：可 pass（`compat_policy` 有实质文本＋`version` 已在）。
- X5：ADR 需记录「为何选严格语义化」，工作量不变。
- T6：契约测试可加「既有七方法仍在且签名不变」的断言，与策略天然对齐。

**对已发布 0.1.2 与现有实现的影响**

- 无代码改动。0.1.2 作为 0.x 基线，后续破坏性变更需升 minor 并在 CHANGELOG 标注。
- `loop-core` 与两个 backend 实现无需调整。

**采用后 X2 能否 pass**：**能**（非空策略＋版本在案）。

## 候选二：宽松（无兼容承诺，只声明弃用周期）

**内容要点**

- 明确声明：0.x 阶段不承诺向后兼容，任何版本都可能破坏。
- 唯一承诺：破坏性变更发布前，至少提前一个版本在 CHANGELOG/README 标注 `deprecated`，并给出替代路径。
- 契约版本仍随包版本走，但不承诺语义。

**收益**

- 与 0.x 现实最一致，几乎不限制演进。
- 实现成本最低，无需维护兼容矩阵。
- 对 0.1.2 零改动。

**代价**

- 对外部消费者最不友好：`published` 状态却无兼容承诺，等于把风险全部转嫁给消费者。
- T6 很难写出有意义的契约测试（只能测「方法存在」，不能测「行为不破坏」）。
- ADR 的「后果」一节会记录一个明显弱点，未来转严格策略时又要再写一次 ADR。

**对 X2／X5／T6 的影响**

- X2：可 pass（文本非空），但**通过的是形式，不是承诺**——需要在 ADR 里如实写明。
- X5：ADR 记录「选择不承诺」，审批时人类需接受该风险。
- T6：契约测试只能覆盖存在性与错误码，覆盖力最弱。

**对已发布 0.1.2 与现有实现的影响**

- 无代码改动；但消费者无法据策略判断升级风险。

**采用后 X2 能否 pass**：**能**（形式满足），但属最弱的一种 pass。

## 候选三：折中（契约版本号＋弃用窗口）

**内容要点**

- 契约版本与包版本**解耦**：`CT-PACT-BACKEND-01@1` 表示契约主版本，包版本可独立走 `0.x`。
- 加性变更（新增可选方法/字段）：升契约 minor，旧消费者不受影响。
- 破坏性变更：升契约 major，且必须满足**弃用窗口**——旧契约面至少保留一个小版本或 30 天（取较长者），期间新旧并存并标注 `deprecated`。
- 弃用窗口结束才可删除；窗口内删除视为违约。
- 契约版本与窗口长度都写入 `compat_policy`，可机器校验。

**收益**

- 解决 0.x 语义歧义：契约版本独立表达「接口面」，包版本表达「实现」。
- 给消费者一个可预期的迁移期，比候选二有承诺，比候选一少一点刚性。
- 弃用窗口是**可判定的数字**，T6 可写「窗口未满不得删除」的测试，X2 的策略也可被后续机械抽查。

**代价**

- 需要维护两套版本号（包版本＋契约版本），并在 release 流程中同步。
- 窗口长度（一个小版本或 30 天）需要人类拍板；选错会增加维护负担。
- 比候选一多一个「窗口计时」的状态，文档与流程成本最高。

**对 X2／X5／T6 的影响**

- X2：可 pass，且 `compat_policy` 含可判定参数（契约版本、窗口），不是纯文字。
- X5：ADR 需同时记录契约版本策略与窗口长度，篇幅略长。
- T6：契约测试可覆盖「七方法存在＋加性变更不破坏旧调用＋窗口内旧面仍在」，三者中最强。

**对已发布 0.1.2 与现有实现的影响**

- 无代码改动；但需在 README 增加「契约版本」小节，声明 `CT-PACT-BACKEND-01@1` 与 0.1.2 的对应关系。
- 下一次破坏性变更起才真正用到窗口；当前无迁移动作。

**采用后 X2 能否 pass**：**能**（且是三种里最可复核的 pass）。

## 选定（人类批准，2026-11-14）：候选三

**选定方案**：契约版本号＋弃用窗口。契约版本与包版本解耦；破坏性变更保留旧契约面「一个小版本或 30 天，取较长者」。

**具体语义**

- **契约版本**：`CT-PACT-BACKEND-01@<major>`。当前发布面记为 `CT-PACT-BACKEND-01@1`，与包版本 `0.1.2` 对应；包版本继续独立演进。
- **加性变更**：新增可选方法、可选字段、可选错误信息，升契约 minor；旧调用不受影响，不触发弃用窗口。
- **破坏性变更**：删除、重命名、改签名、改错误码语义，必须升契约 major，并进入弃用窗口。
- **弃用窗口**：旧契约面在**至少一个小版本或 30 天（取较长者）**内继续可用；期间旧面标注 `deprecated`，README/CHANGELOG 给出替代路径；窗口结束前不得删除。
- **违约判定**：窗口未满即删除旧面 = 违约；未升 major 的破坏性变更 = 违约。
- **版本号示例**：包 `0.2.0` 可继续承载契约 `@1`；契约升 `@2` 时包版本可以是 `0.3.0` 或 `1.0.0`，两者不强制同号。

**选择理由**

1. 当前是 `0.1.2`，候选一的严格 semver 在 0.x 上本身有歧义；契约版本独立表达接口面，定义更干净。
2. 契约已 `published`，候选二「无兼容承诺」对消费者最不利，也会被 ADR 如实记录为弱点。
3. 弃用窗口是数字，可在 T6 契约测试与后续抽查中复核；候选一、二主要是文字承诺。
4. 三种候选对已发布 0.1.2 都没有代码改动；候选三只多一节 README 与 release 流程一个检查点。

**未选方案的放弃理由**

- **候选一（严格语义化）**：不是不可行，而是 0.x 语义需额外解释；若未来升到 1.0，约束会最刚。作为备选保留，若人类后续更看重 npm 习惯可切回。
- **候选二（宽松）**：维护成本最低，但「已发布却无兼容承诺」与 `published` 状态不匹配，T6 也只能测存在性。放弃。

**选定后对检查项的影响**

- **X2**：待 `compat_policy` 按本文填入白板后转 pass；当前仍 fail。
- **X5**：待 ADR 获人类批准后转 pass；当前仍 fail。
- **T6**：待契约测试按本文语义落地后转 pass；当前仍 fail。

## 原推荐（已由人类采纳为选定方案）

**候选三（契约版本号＋弃用窗口），窗口取「一个小版本或 30 天，取较长者」。**

理由：

1. **当前事实是 0.1.2，不是 1.0**：候选一的严格 semver 在 0.x 上语义本身有歧义，需要额外解释；候选三用独立契约版本绕开这个歧义，定义更干净。
2. **`published` 状态需要真承诺**：候选二虽然最省事，但「已发布却无兼容承诺」会被 X5 的 ADR 如实记录为弱点，也不利于后续消费者。
3. **可机械复核**：候选三的弃用窗口是数字，能在 T6 的契约测试与后续抽查中落地；候选一、二的策略主要是文字承诺。
4. **改动成本可控**：三种候选对 0.1.2 都没有代码改动；候选三只多一节 README 与 release 流程的一个检查点。

若人类更看重「少维护、先跑起来」，可退到候选一（严格语义化）；不建议候选二，除非明确本包永远只服务仓内 `loop-core`。
