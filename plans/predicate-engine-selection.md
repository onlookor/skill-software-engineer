# 谓词引擎技术路径选择与收益代价分析

> **状态：分析记录（已裁定）。** 人类于 2026-11-18 批准推荐组合 **A2+B2+C1+D2+E1**；裁定记录见 [`adr/ADR-PRED-ENG-01`](../adr/ADR-PRED-ENG-01-approved-20261118-谓词引擎选型与A2B2C1D2E1落地.md)。本文保留路径摊开与代价分析，不是 ADR，也不是实现计划。
> 本文不含实现代码；不涉及母本、《编译规范》正文、14 张卡正文与 `skills/software-engineering/validators/` 的改动。
> 版本保持 0.9.0；dist 不重打包。

## 0. 结论先行

人类已裁定方向为“造谓词引擎”，不采用“只做可求值子集、其余登记为代理或人工判定”。选型为：

**受限表达式 DSL（A2）＋ 三值语义（B2）＋ 手写 AST 解释器（C1）＋ 33 个卡片谓词名全覆盖（D2，`style` 作为第一个垂直切片）＋ 独立引擎模块（E1，由 `check-card.py`／编译流水线／FVR 调用，`validate.py` 不调用）。**

这不是“通用谓词逻辑引擎”，也不是“整层规则谓词化”。它只覆盖 `predicate_writes` 这一类设计谓词，表达力限定为布尔组合、比较、枚举、集合成员、引用核对与有限域量化；不做递归、函数定义、开放世界推理，不引入第三方依赖。

**工作量（按 §1.5 的估算口径，全部为 `estimate`）**：输出 token 约 56k–91k，输入 token 约 167k–545k，生成侧墙钟约 0.7–3.8 h；不含跨会话复核等待与人类裁定等待。三空间 `applicability` 另计输出 14k–22k token、生成侧墙钟 11–54 min，可延后。

### 1.5 估算口径（token 预算／生成侧墙钟／闸门数）

本节按 PM 的 `spec/ESTIMATION_METHOD.md`（唯一正文）与 `adr/0023-estimation-in-token-wall-gates.md` 计算；单位、公式、校准锚、回填与标注规则以 PM 原文为准，本节只列本仓取值与结果，不另立定义。任何工作量必须同时给出三件并列数：

1. **token 预算**：输入与输出分开，按 PM §1.1 标注 `estimate`／`measured`。
2. **生成侧墙钟**：按 PM §1.2 的公式与系数折算；给区间，不给点值。该数**只覆盖生成与本地工具**，不含跨会话复核等待、人类裁定等待与深夜／周末排期。
3. **闸门数**：按 PM §1.3 列非同源复核轮次、钉扎签收次数、人类决策点。

**本仓计算取值与来源（实测锚与折算系数分开）**：

- **输出 token**：新增／改写行数 × 18。18 是 PM §2 的**折算系数**，不是实测锚；本仓未重标定。
- **输入 token**：输出 × 3–6。PM §2 的原文区间是 **2–6**；本表统一取 **3–6** 作为保守子区间，理由是读入面（220 名跨 17 块、18 张卡、T1–T5 与 5.7）大于 PM 的检查层。全文表格按 3–6 计算，2 只用于与 PM 原文对照。
- **吞吐**：输出 100 tok/s、总 150 tok/s。这是 PM §3.1 的 **D6 实测锚**（实测区间为输出 100–108、总 146–157 token/s）；本仓未实测，直接借用。
- **工具与本地排队系数**：1.5–3。这是 PM §2 的**折算系数**，不是实测锚。
- **对外换算**：1 人日 ≡ 150k 总 token。这是 PM `ESTIMATION_METHOD.md` §5 与 `adr/0023` §2 的对外换算规则，只用于与旧计划、外部排期对照，不用于本仓排期。

**本仓缺什么（不得硬凑）**：

- 本仓**没有**自己的 D6 式吞吐校准锚；100／150 tok/s 是 PM 的实测值，不是本仓实测；
- 本仓**没有** agent 侧 usage 记账，也没有历史批次的“行数—墙钟”对照表；所有 token 与墙钟均为 `estimate`；
- 复核轮次与人类裁定点尚未排期，闸门等待只能给数量，不能给时长；
- 本仓读入面大于 PM 的检查层，输入 token 可能高于“输出 × 6”的上界；无实测，故不虚写上界。

**量级提示（不重复乘系数）**：PM §3.2 的治理／文档类偏差中位 8.69× 是“实际墙钟 ÷ 公式墙钟”，而公式墙钟**不含** 1.5–3 系数。把它直接乘到上面已含 1.5–3 的生成侧墙钟上会重复计一次。正确做法是先去掉系数（0.7÷1.5 至 3.8÷3 ≈ 0.47–1.27 h），再乘 8.69，得约 **4–11 h**。该数只作量级提示，**不构成本仓承诺**，也不写进计划表。

**历史单位说明**：本仓历史文档中仍有人日表述，共 9 处——`adr/ADR-SRC-02-approved-20261106-signals字段方案A.md`（2 处，真实工作量）、`立项-代价字段可算性与PRJ回填.md`（4 处）与 `cost_profile-取值格式方案-20261112.md`（3 处）是量纲定义示例。按 PM `ESTIMATION_METHOD.md` §5，历史文本保留原文、不改写；**本轮新增与改写的文档已统一为 token／墙钟／闸门**，不声称全仓已无人日。

## 2. 与 PM `ADR-0022` 的分歧：正面处理

`ADR-0022` 的标题是“谓词化只做检查层”，其中第 1 条说“不做整层谓词化”，第 5 条把“受限谓词 DSL + 求值器”列为**唯一合理的中期扩展**，第 9 条把它排在 P2。审计把 PM 立场转述为“不造谓词引擎”（**这是审计转述，不是 PM 原话**；PM 原文是“不做整层谓词化”），该转述至少有两种读法：

1. **不造通用谓词逻辑引擎**（z3／Rego／CEL／整层规则谓词化）——这一条软工同样接受；
2. **连受限 DSL 与求值器也不做，只靠 schema + Python**——这一条**只适用于 PM 的检查层**，不能反推到软工。

**为什么软工不能照抄“只靠 schema + Python”**：

- 软工的母本 10.2.3bis 与《编译规范》T1–T5 把“谓词增量”定义为设计状态的权威记录；没有求值，谓词就只是可读注释。PM 的 `ADR-0022` 背景第 2 条自己说：软工的教训不是“谓词化错了”，而是“有语法、没求值”。造求值器正是对该教训的补救，不是对它的否定。
- PM 的对象是 17 个 `check_id`／41 条 A.2 子句，判定面主要是工件 schema 与具名 Python 算子；schema + Python 足以覆盖。软工的对象是 220 个谓词名跨设计事实（`selection_context`、`verdict_table`、`step_log`、`exclusion_record` 等），没有一张等价的工件 schema 可以替代表达式求值。
- PM 的 `ADR-0022` 是 PM 范围的决策，不是跨仓本体论。它明确把三空间谓词排除在 PM 之外，也明确不把“形式层”设为最高权威；这两点软工都不照抄（见 `plans/audit-intake-20261118.md` C-02、C-04）。

**软工应当从 PM 借的四条**（不涉及“不做引擎”）：

1. 语法与翻译分离：解析／arity／类型／枚举／引用闭包／三值求值由确定性程序做；从散文到谓词的翻译只在编写期作为一次性资产，运行期不设翻译位置。
2. 词项闭集：谓词名、关系词、枚举值、字段名必须来自登记表；未登记词项在编写期拒绝，运行期不猜。
3. 权威方向不改：判定以形式层为准，文本以母本为准；谓词通过不等于母本正确，形式缺陷不否定条文效力（0.24.3(3)）。
4. 单写者快照：先做单写者白板快照与比对，多写者合并、并发冲突不在当前范围。

**分歧的落法**：本文推荐“受限引擎”，不是“通用引擎”；这与 PM `ADR-0022` 第 5 条的“受限 DSL + 求值器”同向，与“整层谓词化”相反。若人类认为连受限引擎也不应造，则应回到 `ADR-0022` 的 P0/P1＋代理登记路线；但那条路线已被本次裁定否决。

## 3. 五条选型轴

> 下表工作量为**该轴内部选项之间的相对量级**（`estimate`：输出 token／生成侧墙钟），不是全案总量，也不可跨轴相加。总量见 §4.1。输入 token 按输出 × 3–6 反推，墙钟按 §1.5 公式折算；每个选项另列新增闸门。

### 3.1 轴 A：谓词表达式的载体与语法

| 选项 | 收益 | 工作量（estimate） | 新增判定面 | 新增可被弱模型伪造／套利的面 | 长期维护 | 失效模式与已知天花板 | 不可逆点 |
|---|---|---|---|---|---|---|---|
| **A1 结构化字段**（原子谓词 + 扁平 `all_of`／`any_of`，无嵌套表达式） | 无解析器；schema 直接校验；确定性最强；弱模型最难注入逻辑 | 输出 5.4k–9.0k token；生成侧墙钟 4–23 min；闸门 0 | 名字、arity、字段存在性、扁平组合 | 写一个形状正确但语义错误的原子；空 `all_of` 当恒真；把该表达的东西塞进豁免 | 低 | 无法表达否定嵌套、存在／全称、跨对象比较；复杂谓词只能不断造新名字，词表膨胀 | 低：后续可迁到 DSL，但卡片 schema 要改一次 |
| **A2 受限表达式 DSL**（2.3 BNF 子集：原子、`¬`、`∧`、`∨`、`→`、有限域 `∀/∃`、比较、枚举、集合成员、引用核对） | 能用既有基词表达复合谓词，不必为每个复合造新名；与 2.3／5.7 的三值语法同源；可做类型／arity／词项闭包 | 输出 16.2k–25.2k token；生成侧墙钟 12–63 min；闸门 1 轮复核 | 表达式真值、优先级、量词域、类型、arity、词项闭包 | 恒真式；类型正确但语义错误的原子；量词域取空集／平凡集；“谓词堆砌”把结论埋进长表达式；利用优先级误读 | 中 | 解析器 bug、量词域争议、unknown 爆炸；天花板：无递归、无函数定义、无开放世界 | **高**：AST／语法一旦被 33 名与检查器依赖，改语法就是破坏性变更 |
| **A3 受限 Python 子集**（Python AST 白名单 + 沙箱求值） | 上手快；复用 Python 语义与工具；原型速度最高 | 输出 28.8k–43.2k token；生成侧墙钟 21.6–108 min；闸门另加 1–2 轮安全评审 | 任意白名单 Python 表达式、属性访问、容器操作 | 极大：`getattr`／`__builtins__`／推导式／lambda／异常技巧；弱模型可把逻辑藏进代码；环境差异可被利用 | 高 | 沙箱逃逸、非确定性、版本漂移、“代码就是规范”；天花板：不可移植、不可审计 | **很高**：一旦卡片与检查器依赖 Python 代码，迁回 DSL 成本极高 |

**判断**：A2。A1 无法覆盖 33 名里已有的复合谓词（如 `independently_deployable`、`boundary_direction`），会把词表问题转成“造名问题”；A3 的可伪造面与维护成本不可接受。

### 3.2 轴 B：求值语义

| 选项 | 收益 | 工作量（estimate） | 新增判定面 | 新增可被弱模型伪造／套利的面 | 长期维护 | 失效模式与已知天花板 | 不可逆点 |
|---|---|---|---|---|---|---|---|
| **B1 二值**（true／false；缺失事实按 false 或走带外 `cannot_evaluate`） | 真值表简单；测试矩阵小；实现快 | 输出 5.4k–8.1k token；生成侧墙钟 4–20 min；闸门 0 | 每个原子的 true／false；缺失事实的默认值 | “未知当假”可让弱模型靠不写事实来规避义务；带外 `cannot_evaluate` 又可被忽略 | 低（但语义债高） | 静默排除候选；与 0.18 “未知 ≠ 假”冲突；一旦缺事实，结论不可信；天花板：无法表示部分事实 | 语义契约中：以后加 unknown 是破坏性变更 |
| **B2 三值**（true／false／unknown，Kleene 传播；`cannot_evaluate` 与 `fail` 分开） | 与 2.3／0.18／5.7 P3 同源；未知可带“勘察义务”；支持 FVR；不把缺事实偷换成 false | 输出 9.0k–14.4k token；生成侧墙钟 7–36 min；闸门 1 轮复核 | 每个原子的三值、unknown 传播、unknown 原因、finding 来源 | unknown 可被滥用为“免判”；“勘察义务”可被空转；弱模型可写大量 unknown 让引擎看起来在工作 | 中 | unknown 爆炸（全绿或全 unknown）；下游把 unknown 读成 false；天花板：无概率／置信度，不证明语义正确 | 语义契约：高，需在冻结前定死 |

| 类别 | 条目 | 二值语义 | 三值语义 |
|---|---|---|---|
| 已 closed（复合／入表） | VG-01、VG-02、VG-04（第二次 resolution）、VG-07、VG-08 | 正常求值；缺事实时只能 false 或带外 `cannot_evaluate` | 正常求值；缺事实 → unknown，附勘察义务 |

### 3.3 轴 C：求值器形态

| 选项 | 收益 | 工作量（estimate） | 新增判定面 | 新增可被弱模型伪造／套利的面 | 长期维护 | 失效模式与已知天花板 | 不可逆点 |
|---|---|---|---|---|---|---|---|
| **C1 手写 AST 解释器** | 三值语义、错误定位、finding 来源完全可控；零第三方依赖；确定性最好 | 输出 14.4k–21.6k token；生成侧墙钟 11–54 min；闸门 1 轮复核 | 解释器语义、short-circuit／Kleene 规则、unknown 原因 | 实现 bug 会被当成语义结论；但弱模型不能直接注入代码 | 中 | 解释器 bug、性能（本规模足够）；天花板：只覆盖 DSL 表达力 | 中：IR／AST 形状与 finding schema 一旦被下游依赖，改动有成本 |

| **C3 复用现成约束／规则引擎**（Datalog／z3／Rego／CEL） | 语义成熟、优化好；规则可声明 | 输出 14.4k–27.0k token；生成侧墙钟 11–68 min；闸门另加 1 个依赖引入决策点 | 引擎自身的语义与求解模型 | 引擎特有技巧；依赖版本；模型可写“看起来像规则”的无效规则 | 高（依赖／升级／打包） | 与本仓三值／finding／零依赖纪律不匹配；天花板：引擎模型不是我们的模型 | 高：依赖锁定与语义迁移成本 |

**判断**：C1。C2 把“可审计”换成“少写解释器”，不划算；C3 与“零第三方依赖（除已钉 `jsonschema`）”冲突，且其输出模型与本仓的三值＋finding＋子句署名不匹配。

**判断**：E1。`validate.py` 的 V01–V08 判的是“技能包的复现测试是否可信”，与本轮“设计谓词是否可求值”不是同一对象；混进去会让两边都说不清。V09 仍人工，但可以消费引擎产出的 finding 作为证据。

**接缝与调用关系（推荐 E1）**：

```
编写期（T1，LLM/人）
  narrative_step ──候选──▶ predicate_engine.parse / typecheck ──▶ predicate_writes
                                                          │
编译/gen_cards ──只生成字符串──▶ predicate_engine.validate_artifact ──▶ findings
check-card.py ──validate_card──▶ predicate_engine.validate_card ──▶ findings
                                  （替换 names_in 正则；M3/M4 变薄或退役）
FVR 入口 ──evaluate(snapshot, query)──▶ predicate_engine.evaluate ──▶ 三值 + finding 来源
validate.py V01–V09 ──不调用引擎──▶ 技能包 findings（两套对象，不交叉）
```

- **T1**：翻译在引擎之外（编写期，一次性资产）；引擎只做解析、类型、词项闭包与求值。
- **T2**：引擎计算 `new`／`no_op` 与版本向量增量；入板与回归触发仍由编译／白板流程执行。
- **T3**：引擎检查“谓词写入 ∨ 保全工件”的引用资格；FM-11 事件由调用方生成。
- **T4**：FVR 把白板快照交给引擎求值；引擎不生成 FVR 条目。
- **T5**：引擎不参与批准；谓词写入不等于决策批准。
- **14 张 S6 卡**：第一批客户端；引擎校验 `outputs.predicate_writes` 与 S6 `produces`，不改卡片正文。
- **`validate.py`**：不调用引擎；只共享“finding 长什么样”的约定（若共享，也只共享数据结构，不共享判定链）。

### 4.2 取舍理由

- **为什么是 A2 而不是 A1**：33 名里已经有复合谓词（如 `independently_deployable`、`boundary_direction`）；A1 只能靠不断造新名，词表会从 220 继续膨胀，且复合语义仍无处安放。
- **为什么是 A2 而不是 A3**：A3 的“可伪造面”最大；弱模型可以写一段形状正确、语义错误的 Python，且沙箱与版本漂移不可控。A2 的表达式是封闭语法，至少能被类型／arity／词项闭包约束。
- **为什么是 B2 而不是 B1**：二值在缺事实时必然要外挂 `cannot_evaluate`，等于把三值藏在带外；而 0.18 与 5.7 P3 已经要求 `unknown ≠ false`。B2 与母本一致，且能给“勘察义务”一个正式位置。
- **为什么是 C1 而不是 C2/C3**：本规模（33 名／18 卡）不需要代码生成或外部引擎；C1 的零依赖、可审计、finding 可定位，比“少写几百行解释器”更重要。
- **为什么是 D2 而不是 D1/D3**：D1 只接通 `style`，无法回应审计的 33 名口径；D3 把三空间、方法注册表、开放世界事实一起拉进来，会让第一版引擎失焦。D2 是“能覆盖卡片写入面”的最小完整目标；D3 是下一期。
- **为什么是 E1 而不是 E2/E3**：引擎是设计谓词求值器，不是技能包复现校验器；独立模块能让 `check-card.py`、编译流水线、FVR 各自调用，而 `validate.py` 的 V01–V09 不被稀释。

### 4.3 推荐方案的已知天花板

- 只覆盖 `predicate_writes` 与卡片 S6，不覆盖 220 名全量；不覆盖三空间适用性（延后）。
- 只做单写者快照；多写者合并、并发冲突不做。
- 不做运行期自然语言翻译；T1 的翻译仍是编写期一次性资产。
- 不证明语义忠实：引擎能判“表达式在给定事实下为真／假／未知”，不能判“这个谓词写对了没有”。语义终裁仍在人类评审与 FVR。
- 不证明母本正确；形式通过不等于条文正确（0.24.3(3)）。

## 5. 备选方案

### 备选 1：最小闭环（A1 + B2 + C1 + D1 + E1）

- **适用条件**：只要求接通 `style` 投影；或先把“可求值”跑通再扩。
- **工作量（estimate）**：新增／改写约 2,800–4,400 行；输出 50k–79k token；生成侧墙钟 0.6–3.3 h；闸门 2–4 轮复核、1–2 个人类决策点。
- **代价**：30/33 名未覆盖；复合谓词只能造名或豁免；后续迁到 A2 要改卡片 schema。
- **什么时候选它**：如果人类认为第一版只需要证明“引擎能跑”，不要求覆盖 33 名。

### 备选 2：转译执行（A2 + B2 + C2 + D2 + E1）

- **适用条件**：团队对代码生成与沙箱有经验；需要更高执行速度；能接受“生成代码”作为审计对象。
- **工作量（estimate）**：新增／改写约 3,100–5,250 行；输出 56k–95k token；生成侧墙钟 0.7–3.9 h；闸门另加 1 轮沙箱评审（共 4–6 轮）。
- **代价**：可伪造面、不可审计性、生成代码与谓词的对应关系维护；不建议作为第一版。
- **什么时候选它**：如果性能成为瓶颈，且已有独立沙箱与代码审查流程。

### 备选 3：规则引擎（A2 + B2 + C3 + D2 + E1）

- **适用条件**：只对依赖图／传递闭包做局部推理；愿意引入并锁定第三方依赖。
- **工作量（estimate）**：新增／改写约 3,100–5,350 行；输出 56k–96k token；生成侧墙钟 0.7–4.0 h；闸门另加 1 个依赖引入决策点与升级维护义务。
- **代价**：与零依赖纪律冲突；三值／finding 语义需要适配；不覆盖一般谓词。
- **什么时候选它**：不推荐作为主路径；最多作为依赖图子模块。

## 6. 失效模式、代价与不可逆点

### 6.1 共同失效模式

1. **语法正确、语义错误**：A2 的类型／arity／词项闭包只能保证“写得像”，不能保证“写得对”。弱模型可以写恒真式、错原子、空量词域。必须配黄金负例、变异测试与人工语义复核。
2. **unknown 爆炸**：三值语义下，事实缺失会让大量谓词变 unknown；如果没有 unknown 预算与覆盖率指标，引擎会“全绿但无用”。需要把 unknown 原因与勘察义务登记为 finding。
3. **迁移漂移**：14 张卡的 `predicate_expr` 是自由字符串，迁移到 AST 时可能出现“解析失败—静默改写—看起来通过”。迁移必须产出逐卡报告，失败即停，不得自动改写。
4. **两套判定并存**：`check-card.py` 的旧正则与引擎并行时，可能出现“旧正则绿、引擎红”或反之；必须明确以引擎为准，旧正则只做过渡，并在 CHANGELOG 记录退役点。
5. **实现 bug 被当语义结论**：三值传播、量词域、优先级都容易出错；必须用负例与差分测试锁住，不能只测正例。

### 6.2 不可逆点

| 不可逆点 | 为什么不可逆 | 什么时候必须定 |
|---|---|---|
| AST／语法与词项闭包 | 33 名与检查器一旦依赖，改语法是破坏性变更 | 设计文档冻结前（P0 通过时） |
| 二值／三值语义契约 | 下游 finding、FVR、报告都按它解释；后加 unknown 是语义变更 | 设计文档冻结前 |
| finding schema 与引擎 API | `check-card.py`／编译／FVR 一旦接入，改字段要全链迁移 | E1 接入前 |
| 33 名与卡片 schema | 改名／改 arity 要重迁 14 卡 | D2 开工前 |
| Python 子集（若选 A3） | 代码成为规范，迁回 DSL 成本极高 | 不建议选；若选，必须在第一版前定 |
| 外部引擎依赖（若选 C3） | 版本／打包／语义锁定 | 不建议选 |

**可逆／可延后的**：三空间 `applicability`（D3）是加法，不改变已覆盖的 33 名；全 220 名求值、跨方面合并、多写者、性能／UI 都可后置。

## 7. 与设计文档冻结口径的衔接（已获批）

设计文档不等到 P0 结束后再写。口径为：

- **随 P0 同步成稿**：`plans/predicate-ization-design.md` 与 P0 定义工作同一批推进；它承载 D1–D4 与 AST／类型／三值／编译债务的定义，计划只保留顺序、出口与验收。
- **每标一批黄金样本回改一次定义**：设计文档随第 3 节黄金样本批次更新；不攒到最后。
- **P0 通过时冻结**：四组证据全过、P0 出口达成时，设计文档冻结为 v1.0（draft → frozen）。
- **冻结之后才允许写 AST 与求值器实现**：未冻结前不开工解析器／求值器／检查器；冻结后实现以设计文档为规范目标。
- **P0 未通过**：设计文档保持 draft，不冻结、不开工；不得用“先写实现再倒推定义”绕过。
